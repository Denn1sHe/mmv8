## 1. D1 —— DOM 内核（arena + generation）

### 1.1 独立结论

**同意「扁平 arena + 下标 + generation」为主形态**（brief 方案 A），但**不同意**其配套三条细节，且**不同意 R4 的对策形态**。
推荐按 §1.4 修正后落 ADR。方案 B（`Rc<RefCell<Node>>`）与方案 C（`slotmap`）**同样被驳回**（理由我另附，见 §1.5）。

### 1.2 决定性理由（含源码原文）

**F1 —— U-7（`NodeId` 与 `JsHandle` 位序一致）**：**未攻破**。`crates/engine-v8/src/abi.rs:59-80`：

```rust
pub struct JsHandle(u64);
impl JsHandle {
    pub const fn new(index: u32, generation: u32) -> Self { Self(((generation as u64) << 32) | (index as u64)) }
    pub const fn index(self) -> u32 { (self.0 & LOW_HALF_MASK) as u32 }
    pub const fn generation(self) -> u32 { (self.0 >> 32) as u32 }
}
```
施工图 §1.2 `NodeId::new(index, generation)`（高 32 = generation，低 32 = index）**逐位一致** ⇒ `raw()` 可直接作 `node_map` 的 u64 key。**U-7「确定」成立。**

**F2 —— 「同一节点同一 wrapper」在弱句柄回收后不成立（攻破 brief 优点④与 §6.1 的乐观表述）**：`crates/engine-v8/src/node_map.rs:28-38`：

```rust
pub fn bind(&mut self, node: u64, handle: WeakJsHandle) -> Option<WeakJsHandle> {
    if let Some(existing) = self.by_node.get(&node) { return Some(*existing); }   // ← 只看有无比对，不判存活
    ...
}
```
`by_node` 永不因 GC 自动清除（GC 只清弱槽本身，不清这张 `HashMap`）。一旦 wrapper 被回收：
- `handle_for(node)` 仍返回**已死的** `WeakJsHandle`；
- 施工图 §1.2 `PageBinding::wrapper_for` **没有**规定此时的行为。若按 `node_map` 语义「复用既有」，则 `resolve_weak` → `Collected` ⇒ 报错（**节点再也拿不到 wrapper**）；若走「重建 wrapper」，则必须**覆盖** `by_node` 中的死句柄——但现有 `bind` 直接 `return Some(existing)`，**结构上拒绝覆盖**。
⇒ brief §6.1 把该裂缝列为「不确定点」是诚实的，但 §0 与 §6 优点④却写「由已验收的 node_map 承担」——**二者不兼容**：现有 `node_map` 无法承担「回收后重建」，这是跨 crate 契约缺口（须改已验收代码）。

**F3 —— 「不回收 arena 槽」与施工图 §4 测试契约互斥**：brief §6.2 推荐「删除只脱离树，**不**回收 arena 槽（槽回收另设显式 dispose，本轮可不做）」；施工图 §1.2 `NodeTree` 的公开面无 `dispose`，`free: Vec<u32>` **无处入栈** ⇒ generation **永不递增** ⇒ 施工图 §4 `web-dom::tree` 的 `nodeid_generation_reuse`（「复用槽旧 id 失效」）**无法经公开面构造**。测试契约与设计形态互斥。

**F4 —— R4 的「不重入」是纪律，与 D2 否定方案 C 的标准自相矛盾**：D2 brief §3 方案 C「缺点与风险」原文写「**正是本仓想避免的「靠纪律」形态**」；而施工图 §6 的 **R4 对策原文**是「**纪律：不重入（借用不跨回调）**；sink 只在 `feed` 帧内借；binding 回调内不触发解析」。**同一批文档对同类问题用了两套标准**。更关键：R4 的风险是**运行期 `RefCell` panic**（施工图 §4「覆盖率盲区」自己承认「`Rc<RefCell>` 运行期借用 panic 用『不重入』单测 + 代码评审兜」），而本仓既有形态**已经给出结构解**——`crates/sdk-python/src/lib.rs:122` 等 6 处一律 `try_borrow_mut().map_err(|_| reentrant_pyerr())?`（把重入变成**可判定错误**而非 panic）。D1 **应当沿用同一形态**，而不是退回纪律。

**F5 —— 隐藏规范负担：`MutationObserver` 的归属类型整体缺失**：施工图 §1.1 文件清单只有 `web_dom::mutation::{MutationRecord, MutationBuffer}`；**没有** `MutationObserver` 观察器注册表、`observe` 选项（childList/attributes/subtree/attributeOldValue…）、`takeRecords`。但施工图 §3.7/§3.9 与 `sequence-diagram-g2.mermaid:75-76` 都要求「交付 MutationObserver 回调」，而回调是 **JS 函数** ⇒ 必须由某处持 `WeakJsHandle`（C-2）。⇒ 「最小但规范」的宣称下藏着一个**未归属的组件**。

**F6 —— `class_list` 双真相源**：施工图 §1.2 `ElementData{attrs, class_list}` + §2.2「`class` 同步维护 `class_list`」。两个可写真相源需靠纪律保持同步（`setAttribute("class",…)`、`className=`、`classList.add` 三条路径）；建议改为**惰性派生**（`class_list` 由 `attrs` 按需分解）。

### 1.3 对 brief 论据的攻破结果

| brief 论据 | 结果 |
|---|---|
| 优点③「DOM 侧不持 JS 引用 ⇒ 结构上不可能造出 ADR-0007 的跨语言环」 | **未攻破**（我核对了方向：JS→Rust 的强引用是 native 闭包捕获 `Rc`，方向反向，不成环；`NodeId`/`WeakJsHandle` 侧确实无强 JS 引用） |
| 优点②「旧 `NodeId` 可判定失效」 | **未攻破**——但**前提失效**：见 F3，generation 永不变 ⇒ G2 内不可判定 |
| 优点④「同一节点同一 wrapper 由 node_map 承担」 | **攻破**（F2） |
| §6.2「删除只脱离树、不回收槽」 | **攻破**（F3 与施工图 §4 互斥） |
| R4 的「不重入＝纪律」 | **攻破**（F4：与 D2 标准冲突 + 本仓已有结构解） |
| 方案 B（`Rc<RefCell<Node>>`）缺点①「无 generation ⇒ ABA」 | **未攻破**（成立）；但 brief 未提方案 B 的**致命**点：与施工图 §1.2 的 `NodeData`（下标树链、可序列化、零 unsafe）不兼容，且 `Rc` 环 + `Weak` 父指针在 `remove_from_parent`/`reparent_children` 下极易写成泄漏——结论相同、理由更硬 |
| 方案 C（`slotmap`） | **同意拒绝**，但 brief 的「`NodeKey` 不能稳定 u64 序列化」是**推测**（未给源码）；更硬的拒绝理由：新增依赖须过 `deny.toml` + 「类型面只用本仓定义类型」（ADR-0009）+ 与 `engine-v8::node_map` 的 u64 key 需再适配层（多一个真相源）。建议改以这三条为由，避免用未证实的 crate 行为当主论据 |

### 1.4 修正项（具体要点，非替代设计）

1. **`wrapper_for` 的回收后语义必须写死**：`resolve_weak → None` 时**新建 wrapper 并覆盖 `by_node`**；为此 `NodeMap::bind` 需新增/改用「覆盖死亡弱句柄」的语义（例如新增 `bind_force` 或让 `handle_for` 先判存活）。落 engine-v8 的**独立 ADR/变更**，并加测试 `node_wrapper_recreated_after_collection`。
2. **删除≠回收的解耦必须显式化**：给出 `dispose(NodeId)`（可 `pub(crate)`）或明确「G2 不做槽回收」，**并据此改施工图 §4 的 `nodeid_generation_reuse`**（否则该测试不可满足）。
3. **R4 升级为结构保证**：跨 crate 边界凡借 `Rc<RefCell<NodeTree>>`/`PageShared` 一律 `try_borrow`/`try_borrow_mut` → 返回 `DomError`/`PageError`。加专测 `refcell_reentry_is_error_not_panic`（构造「native fn A 借树 → 回调 JS → native fn B 再借树」路径——`native_fn.rs:96` 的 `in_callback` **不阻断**这种嵌套 native fn，见 §4.3）。
4. **明确 `MutationObserver` 最小类型与归属**（crate/模块/是否用 `WeakJsHandle` 槽），补 §3.7 主语。
5. `class_list` 改惰性派生（或明确单一写点）。

### 1.5 我不采纳的替代（供裁决参考）

- 方案 B、C：同 brief 结论，但**换更硬的理由**（见 §1.3 表）。**同意** brief 推荐 A。

## 2. D2 —— 解析器宿主 + 执行协议 + 调度器核心（含我必查的子问题 4）

### 2.1 独立结论

**同意「任务化执行 + 单线程消息泵」（方案 A），U-1 源码级成立**；**不同意**其「有界/可被打断」的性质声明，且发现**两处设计契约不可编译**、**一处偏离技术方案明文硬要求**、**一处交付边界自相矛盾**。

### 2.2 U-1 源码级核实（未攻破）

### 2.3 攻破点 1（最重要）—— 单脚本任务**不可被打断**，且**违反技术方案明文**

- `RunLoop` 的预算（`max_tasks`/`deadline`）只能在**任务与任务之间**检查；脚本是在**任务内**执行 `realm.eval(script_text)`。
- `crates/engine-v8/src/realm.rs:205-258` 的 `eval`/`eval_impl` **全程无墙钟守卫、无 `terminate_execution`**；唯一有守卫的是 `perform_checkpoint`（`realm.rs:489-527`：起 watchdog 线程 → 超时 `terminate.terminate_execution()` → `cancel_terminate_execution()` → 报 `MicrotaskBudget`）。
- 技术方案 §6 原文（docx 行 186）：「**执行超时由独立 watchdog 请求 V8 终止；终止后的任务明确标记失败并销毁受影响执行单元。** 同步宿主回调必须有截止期限……」
- ⇒ 页面含 `<script>while(true){}</script>` 时，`run_until(max_tasks=1, deadline_ms=1)` **会永久挂起**。这与 §16「禁止 eval 悄悄无限等待」（行 410）直接冲突。
- ⇒ 施工图 §2.1 原文「本图默认任务化（**保证 `run_until` 有界、可被打断**）」与 D2 brief 方案 A 优点①「`run_until` 天然**有界**……兑现 §16」是**过度声明**：任务化只界「任务数/任务间墙钟」，**不界任务内**。

**修正（择一，建议 a）**：
- (a) 把 G1 的 watchdog 形态**继承到所有执行 JS 的任务**：`ScriptBlocking`（及 `Network` resolve、`MutationObserver` 交付）的 `eval`/`call` 用同一 `TerminateHandle` + 独立线程，上限取 `RunBudget.deadline`（或独立 `script_deadline_ms`）；打断后按 `JsErrorKind::Terminated` 标记该任务失败（`error.rs:20` 已有 `Terminated` 变体，语义吻合）。加专测 `stuck_script_terminated_by_deadline`。
- (b) 次选：显式登记为 G2 已知局限 + `capabilities` 标志 + 专测登记「无法打断」。**但不得保留「可被打断」的无条件声明。**

### 2.4 攻破点 2 —— `run_until(budget, self)` **不可编译**（两文档间调用形态漂移）

`sequence-diagram-g2.mermaid:30` 原文：`RL->>BC: run_until(budget, self)`；施工图 §1.2 `RunLoop::run_until(&mut self, budget, exec: &mut dyn TaskExecutor)`，而 `TaskExecutor` 由 `BrowsingContext` 实现（`class-diagram-g2.mermaid:293`）。字面写法 `self.runloop.run_until(b, self)` 同时要求 `&mut self.runloop` 与 `&mut self` ⇒ **E0499 双重可变借用**。
**修正**：施工图须写明「先解构字段再传独立 executor」形态（本仓既有先例：`realm.rs:267-272` 的 `let Self { isolate, context, handles, .. } = self;`）：
```rust
let Self { runloop, realm, shared, binding, .. } = self;
let mut exec = Exec { realm, shared, binding };   // 独立结构实现 TaskExecutor
runloop.run_until(budget, &mut exec)
```
不改语义，但**必须落进 §1.2/§2.1**，否则工程师按图写不出。

### 2.5 攻破点 3 —— `NativeFn: + Send` **阻断** binding（跨 crate 编译阻断，详见 §5 B1）

`crates/engine-v8/src/native_fn.rs:36`：
```rust
pub type NativeFn = Box<dyn FnMut(&mut Realm, &[HostValue]) -> Result<HostValue, JsError> + Send>;
```
而 `Realm::new_function`（`realm.rs:401`）/`install_native_at`（`realm.rs:421`）是 `navigation` 注册原生函数的**唯一安全路径**（铁律 5：navigation 零 `v8::`）。施工图 §1.2 的 `PageBinding` 持 `Rc<RefCell<NodeTree>>` + `node_map`（`PageBinding{tree: Rc<...>, node_map, parser_active: Rc<Cell<bool>>, writes: Rc<RefCell<Vec<String>>>}`），§2.5 的 `__iv8_fetch` 亦须访问 `NetworkService`——`Rc`/`PageShared` 全是 **`!Send`** ⇒ 捕获它们的闭包**无法**成为 `NativeFn`。全局仅此一处 `Send`（`grep Send` 全仓 engine-v8 只命中此行的 `+ Send`），且 `Realm` 本身因 `Box<OwnedIsolate>` 就是 `!Send` ⇒ 该约束**无必要**。
**修正（择一，须落 ADR）**：(a) 去掉 `NativeFn` 的 `+ Send`（engine-v8 改动，按铁律 6 评估；`Realm` 单线程，去掉此约束不引入跨线程能力）；(b) 提供「不捕获的 native fn + 侧通道状态」机制（沿用 `REALM_DATA_SLOT` 范式：再加一个 data slot 存 `*mut PageShared`，native fn 只按 id 取状态）。

### 2.6 攻破点 4 —— `document.write` 多次调用的**插入顺序会倒置**

施工图 §1.2 `ParserHost{ pending_writes: VecDeque<StrTendril> }` + §1.2 `enqueue_document_write(&mut self, text: &str)`「**以 `push_front` 表达插入点**」。若逐条 `push_front`，`write("a"); write("b");` ⇒ 队列 `[b, a]` ⇒ **与文档顺序相反**。ADR-0006 探针只测了**单条**注入（`poc/t2_3_html5ever_pause`，(d) 断言单条），未覆盖多条。
**修正**：`resume` 注入时**逆序** `push_front`（或先拼接再注入），并加回归测试 `document_write_multiple_in_order`——这正落在 ADR-0006「插入点顺序必须写成回归测试，否则任何『简化队列操作』的改动都会静默破坏 `document.write` 语义」的射程内。

### 2.7 攻破点 5 —— MutationObserver 交付边界文档内自相矛盾

- D2 brief §6.4 原文：「G2 计划：编排层在 **checkpoint 前先跑观察器回调**，再 `perform_checkpoint`。」
- 施工图 §2.2：「变更记录……**交付时机 = 微任务 checkpoint**」。
- `sequence-diagram-g2.mermaid:72-76`：先 `perform_checkpoint()` → 回调更新 DOM → **再**交付 MO 回调，并注「**先于 checkpoint 的宿主微任务**」。**三处描述不一致**。
- 技术方案 §6（docx 行 161、169）把 `MutationObserver` 明确列为**微任务**、须「接入相应调度协议」「追踪嵌套与异常」。
- 结构事实：V8 不允许宿主把 MO 回调**插进**原生微任务队列（`perform_microtask_checkpoint` 一次性跑完 V8 队列）⇒ 本设计的「前/后跑 MO」都是**规范偏差**。
**修正**：把交付点定死为一处，并**显式登记这是相对规范的偏差**（连同它与 Promise `then` 的相对顺序），绑一条纵向样例断言（§3.9 已有 Promise→DOM→MO 链路），不要留下三种说法。

### 2.8 子问题 4（我必查项）—— 调度器核心形态逐项评

| 子项 | 我的判断 |
|---|---|
| 任务源分队列（`TaskSource` 6 值 + 同源 FIFO） | **同意**；与 §6 行 165-166「定时器、网络、用户输入、消息等分队列；源内保持规定顺序」一致 |
| `run_until` 有界（`max_tasks` + 墙钟） | **部分**——任务间有界，**任务内无界**（§2.3）。`DeadlineExceeded` 的检查点必须写明「任务边界」 |

## 3. D3 —— 资源等待 + 导航 + PyO3 控制面

### 3.1 独立结论

**同意方案 A 主干**（有界推进 + 入队回填 + epoch 作废 + 绕开 `PromiseResolver`）；**但三处规格缺口必须闭合**（导航语义登记、res/rej 归属、PyO3 重入覆盖），另有 1 处提醒。

### 3.2 未攻破（确认为正确）

- `run_until` 队列空但 `has_pending_io()` ⇒ `WaitingIo`：**逐字对齐**技术方案 §6 行 185「缺少在线响应时**返回 waiting_io，不凭空完成请求**；`advance` 也不替网络后端假造成功」。
- `complete` **只入队**、resolve 在 `run_until` 内：对齐 §6 行 178「**I/O 线程仅投递纯数据；页面线程创建 JS 值并 resolve**」与 ADR-0014 决策 1「回调总在已持 GIL 的线程上执行；派发路径**不发起跨线程阻塞式取锁**」。brief 方案 B（同步 resolve）被攻破的理由（重入 + 越预算 + 跨线程）**成立**。
- 绕开 `PromiseResolver`：与 ADR-0014 / ADR-0012（`PromiseResolver` FATAL 属 G1 K-11 遗留）一致；**同意**「普通闭包 + `HandleLease` 存 res/rej」为 G2 形态。
- 与 §16 行 412 的「attach/detach」字面：ADR-0014 决策 6 + ADR-0012 修正注记已把该条**限定**为「回调入口线程未持 GIL 时」；G2 同线程路径**不适用**。按 `AGENTS.md` 优先级（ADR > 技术方案）D3 取舍**成立**——但 D3 brief 只在 §5 泛引 ADR-0014，建议**显式引用该修正注记**以闭合字面。

### 3.3 缺口 1（攻破施工图 §7 U-9 的推论）—— 单 Realm 下「导航」被高估

- 施工图 §7 U-9 原文判断：「`BrowsingContext` **全程单 Realm（不切换）** ⇒ 与 G1 同构、**无碍**」。
- 技术方案 §4 行 168 要求「**新导航撤销旧文档任务**和资源消费者，延迟返回的旧响应不能写入新页面」；行 146「**关闭与导航不能只清空全局变量**」。
- 单 Realm/单 Context 下，epoch 只能挡「**任务落地**」；**旧文档的 JS 全局（`document`、DOM wrapper、pending Promise 的 resolve 闭包）在同一 Context 内仍存活**。⇒ 测试 `stale_epoch_task_dropped` 通过，**不能**读作「旧文档已撤销」。
- 更具体：施工图 §1.2 `PageShared.tree: Rc<RefCell<NodeTree>>` 在 `BrowsingContext::new` 建；`load(&mut self, snapshot)` 若**复用**同一棵树，则 `NodeId` 的 `(index, generation)` 可跨导航**别名**（新树里的节点落到旧下标 ⇒ 旧 `node_map`/wrapper 指向新节点）。这与技术方案 §5「节点池复用也不能让旧句柄指向新节点」同源风险。
**修正**：(a) 在 U-9/§2.4 **显式登记**「G2 导航 = epoch 作废 + 重建文档/绑定；不新建 Context/Realm，旧 JS 全局保留」；(b) 规定 `load` **分配全新 `NodeTree`**（generation 基线单调）并清空 `NodeMap`（`node_map.rs:53 unbind`/重建 `PageBinding`），加测试 `node_id_not_aliased_across_navigation`。

### 3.4 缺口 2 —— res/rej 的 `HandleLease` **归属未定**，隐藏新的跨 crate 依赖

施工图 §2.5「`__iv8_fetch`……把 `res`/`rej` 经 `Realm::root` 存为 `HandleLease`（**按 `RequestId` 索引**），并向 `NetworkService` 登记请求」；但 §1.2 `NetworkService{ pending, log, transport, next_id }` 的 `PendingState` **类型未定义**：
- 若 `PendingState` 持 `HandleLease` ⇒ `network` crate 必须依赖 `engine-v8`（**§1.1/§8 未列的新跨 crate 依赖**），且 `network` 类型面出现 `HandleLease`（C-2 只禁 `web-dom`/`web-events`，故合法——但须登记，否则评审下一轮会当违规）。
- 若放在 `navigation::page`/`PageBinding` ⇒ `network.complete` 与 lease drop 之间需跨模块握手，接口要写清。
**修正**：明确 lease 表归属（建议 `navigation::page`，保持 `network` 零 `engine-v8` 依赖），并写死 **`complete` 重复调用的语义**（幂等 `Ok` 或可判定错误 `AlreadyCompleted`——brief §6.2 目前是开放问题）与 `abort_epoch`/`close` 的 drop 时机。

### 3.5 缺口 3 —— PyO3 重入守卫**未覆盖 G2 新增入口**（同 ADR-0014 决策 3 的「覆盖全部入口」）

ADR-0014 决策 3 原文：「`Realm.in_callback` **必须 RAII**，且**覆盖全部重入入口**」。G1 的 **Python 侧**做法是 `crates/sdk-python/src/lib.rs:122/134/148/186/199/210` 六处 `self.plane.try_borrow_mut().map_err(|_| reentrant_pyerr())?`（把重入变成可判定错误）。G2 新增 `run_until`/`page.load`/`network.complete`/`input.dispatch`，且 `PyPage`/`PyNetwork`/`PyInput` **共享**同一 `BrowsingContext`（§1.2 注释原文「共享 `BrowsingContext`（经 `Py<PyContext>` 或 **Rc**）」——本身是个未定的「或」）。若新增入口不用 `try_borrow_mut`：`run_until` 持 `&mut` 跑 JS → JS 回调 → Python → `ctx.network.complete()` ⇒ **`RefCell` panic**（而非可判定错误），违反铁律 10「不静默降级」。
**修正**：把「G2 全部 PyO3 入口一律 `try_borrow_mut` → 投影为 `ReentrantEval`」写为 **S14 首步验收项**，加专测 `py_control_reentry_is_error`；并把 `PyPage/PyNetwork/PyInput` 的**所有权形态定死**（建议各持 `Rc<RefCell<BrowsingContext>>`，**不**用 `Py<PyContext>` 反向引用，避免 Python 级环 + 借用交织）。

### 3.6 提醒（不阻断）

`network.complete` 的**批量接口**（§16 行 412「大量请求采用批量消息接口」）：G2 单条 `complete(id,resp)` 与 §16 的批量建议并存不冲突（G6 在线传输再定），但应在 D3 登记「批量接口留 G6」，避免被读成遗漏。

## 4. D4 —— 输入事件最小模型（聚焦红队）

### 4.1 独立结论

**同意「显式 target 可信事件、命中测试推 G3」**（与几何 stub 口径自洽；不做=不强上假绿，符合本仓「不假绿」纪律）。**但**分派语义有 3 个破坏点 + 1 个安全窗口，须在落 ADR 前修正。

### 4.2 破坏点 1 —— 「一次 `plan_dispatch` 即快照」**不足以**表达规范的监听器变更语义

施工图 §1.2 / D4 brief §3 原文：`plan_dispatch(tree, registry, target, event) -> Vec<DispatchStep>`，`DispatchStep{ listeners: Vec<ListenerRef> }`，注释「同一次 dispatch 内不变即为『快照』语义」。问题：
1. **取快照的时机与主体被混淆**：规范在**构建事件路径时**克隆各目标的监听器列表（即任何监听器**运行之前**）；`DispatchStep` 里的 `listeners` 是**值拷贝**。
2. **dispatch 期间的 `remove` 必须生效**：规范用监听器条目的「removed」标志，在**调用时**跳过已被移除者。值拷贝的 plan **结构上做不到**——前一个监听器调 `removeEventListener` 移除「后面的」监听器，plan 仍会触发它。
3. brief §3 只列了「once ⇒ 触发后从注册表移除」，**未覆盖**「任意 remove 在 dispatch 期间生效」「dispatch 期间 add 不生效」两条。
**修正**：plan 存**稳定注册 id（u64）** + callback/options；调用前向注册表查活性（`once` 与 `removeEventListener` 共用「移除即置 dead」路径）。加测试 `listener_removed_during_dispatch_not_invoked`、`listener_added_during_dispatch_not_invoked`。
> 诚实边界：DOM 规范对「快照时机/at-target 调用顺序」的**精确条文**本机无副本、本轮不联网 ⇒ 上述第 1、2 点是我基于规范结构的推断，**须以固定修订版规范或 WPT 子集锚定**后固化（见 §6）。但第 3 点（brief 未覆盖 remove/add 语义）不依赖条文即可确认。

### 4.3 破坏点 2 —— 注册/移除的**匹配与去重**不符规范

施工图 §1.2 / D4 brief §3：
```rust
pub struct ListenerRegistry { /* map: NodeId -> Vec<ListenerRef> */ }
impl ListenerRegistry {
    pub fn add(&mut self, target: NodeId, type_: &str, l: ListenerRef);
    pub fn remove(&mut self, target: NodeId, type_: &str, l: ListenerRef);
}
```
- `add` **无去重**：规范「add an event listener」在「已存在同 `(type, callback, capture)` 条目时直接返回、不重复添加」。现状会让同一回调注册两次就**触发两次**。
- `remove` 以**整个 `ListenerRef`**（含 `passive`/`once`）匹配：规范「remove an event listener」只按 `(type, callback, capture)` 匹配，忽略 passive/once。现状会导致 `addEventListener(f, {once:true})` 后 `removeEventListener(f)`（不传 once）**移除不掉**。
**修正**：`add` 去重（键 `(type, callback, capture)`）；`remove` 只按 `(type, callback, capture)` 匹配。加测试 `duplicate_add_is_noop`、`remove_ignores_passive_once`。

### 4.4 破坏点 3 —— at-target 的「拆两段」模型待规范锚定

施工图 §1.2 / `plan_dispatch` 生成 `capture → at-target(capture) → at-target(bubble) → bubble`；§3.6 测试 `listener_phase_order_capture_target_bubble`。该拆法在实现中常见，但**规范里 target 上两类监听器按注册顺序混合调用、`eventPhase` 取 AT_TARGET**；若按现模型，`capture=true` 的 target 监听器会被**排到所有 `capture=false` 之前**，与规范的注册序不符。⇒ 须以规范/WPT 锚定；加 `listener_order_at_target_mixed_registration` 契约测试。

### 4.5 安全窗口 —— `resolve_weak` 与 `call` 之间的 GC 窗口是**纪律**不是结构保证

D4 brief §7.3 / 施工图 §2.3：调用前 `resolve_weak(w)` → `WeakJsHandle`，回收即跳过。但施工图 §1.2 的 `Realm::resolve_weak(&mut self, w) -> Result<Option<HostValue>, JsError>` 返回的 `HostValue::Function{ handle: JsHandle }` 中 **`JsHandle` 仍是弱槽下标（不 root）**，`call` 时**再次** `handles.resolve`（`realm.rs:357`）⇒ **两次解析之间存在回收窗口**。当前编排里两步之间无分配 ⇒ **实际安全**，但这是**「两步之间不许分配」的纪律**，一旦编排被改动就静默失效（失败形态是可判定的 `Collected`，尚不 UB）。
**修正**：在 `engine-v8` 增 `call_weak(w, this, args)`（解析+调用原子）或让 `resolve_weak` 返回带 lease 的值；监听器调用只走该原子入口。加测试 `listener_collected_before_call_skipped`。

### 4.6 `UserActivation` 最小口径 vs §7 原文

技术方案 §7 行 195 原文：「宿主 input 接口生成可信模拟事件并**更新 pointer、button、focus 和 user activation 状态**」；行 196「click、focus、表单提交、键盘输入的**默认动作采用统一状态机**」。G2 只做「`sticky` + 可信 click/keydown 置位 + click⇒聚焦」⇒ 相对 §7 是**范围缩减**（pointer/button 状态、统一状态机未兑现）。这不是「假绿」（D4 已诚实登记为 G3），但**必须与几何 stub 同规格**（`capabilities` 显式项 + 文档登记），否则会被读成 §7 已实现。另：`UserActivation{sticky, transient}` 的 `transient` 在 G2 **无消费方** ⇒ 建议**删除或明确「G2 不置位、G3 再用」**，避免「有字段＝已实现」的误读。

### 4.7 对 brief 论据的攻破结果

| brief 论据 | 结果 |
|---|---|
| 优点①「不需要布局即可工作」 | **未攻破** |
| 优点②「分派算法是纯函数，易测」 | **部分攻破**：`plan_dispatch` 纯，但**可观测语义**（once/remove/add）不在纯函数内，靠编排层纪律；纯函数化反而**掩盖**了 §4.2/§4.3 的规范负担 |

## 5. 阻断项（落 ADR 前必须闭合）

> 阻断 = brief 与施工图/ADR 互斥、推荐方案有不可修补缺口、或两文档间签名漂移。每条给**精确位置**。

- **B1（D2，跨 crate 编译阻断）**：`NativeFn: + Send`（`crates/engine-v8/src/native_fn.rs:36`）与 `PageBinding`/`__iv8_fetch` 需捕获 `Rc<RefCell<…>>`/`PageShared`（`!Send`）**互斥**；`Realm::new_function`/`install_native_at`（`realm.rs:401/421`）又是 navigation 唯一安全注册路径（铁律 5）。位置：施工图 §1.2 `PageBinding`、§2.5 `__iv8_fetch`。**须裁决 (a) 去 `+ Send` 或 (b) 侧通道状态。**
- **B2（D2，偏离技术方案明文硬要求）**：脚本任务内 `eval` 无 watchdog ⇒ 违反技术方案 §6 行 186「执行超时由独立 watchdog 请求 V8 终止」。位置：施工图 §2.1 步骤 3-4、§6 R6；D2 brief 方案 A 优点①（「天然有界」）。**须补 watchdog+`terminate_execution`（继承 G1 `realm.rs:489-527` 形态）或降级声明+登记。**
- **B3（D2，两文档间签名/调用漂移，不可编译）**：`run_until(budget, exec=self)` 双重可变借用。位置：`docs/sequence-diagram-g2.mermaid:30`、施工图 §1.2 `RunLoop::run_until` / `BrowsingContext::run_until`。**须写死解构 + 独立 executor 形态。**

## 8. K-11 消解后的增量观点（≤10 行）

1. **边界更新**：模块脚本不再作「待 K-11」——静态 import 原已可用（`realm.rs:607` `instantiate_module` + `module_resolver`），动态 import 现可复用；施工图 §7 U-11 应改为「K-11 已消解，模块脚本可纳入 G2 最小面」。
2. **最大技术风险（结构约束类）**：`eval_module`（`realm.rs:547-625`）是**同步**的——`instantiate_module` 会**同步**回调 `module_resolver`（`:699-711`）。若模块图里有任何 specifier 需现取（OfflineBundle 未命中），该路径**无法表达「等 I/O」**（不是 `WaitingIo`，而是同步栈内必须给出答案），`run_until` 的任务模型救不了它。⇒ 必须**约束**为：G2 的模块图在 `page.load` 前由 Host 用 `set_module_host` 提供、**整图可同步解析**；未命中 specifier ⇒ 模块加载**可判定失败**，不得退化为等待。
3. **必要约束**：① module 是 deferred 语义 ⇒ 不复用 `TaskSource::ScriptBlocking`，另立 defer 队列，执行点固定在「解析完成之后、`DOMContentLoaded` 之前」，并把 classic-defer / module / DOMContentLoaded 三者相对顺序写成回归测试（§3.8/§3.9）；② TLA 在 G2 最小面**显式报错**（`module.evaluate` 得 pending ⇒ 必须有对策，否则静默挂起）；③ ADR-0015 的「空返回纪律」须同时覆盖 `module_resolver`（其签名为 `Option<Local<Module>>`，返回 `None` 的语义要与「解析失败」区分，不得回到空 `MaybeLocal` 触发路径）；④ **B2 同样适用**：`<script type=module>` 内的死循环/超长求值仍是「任务内不可打断」⇒ 若采纳 B2 的 watchdog，须覆盖模块求值任务。
4. **不改动前述结论**：B1/B2/B3/B6 与 D2/D3 各项修正**均不变**；模块纳入只**新增**上述约束，不消解任何阻断项。
