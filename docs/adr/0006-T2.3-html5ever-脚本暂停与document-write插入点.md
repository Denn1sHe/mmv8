# ADR-0006：T2.3 结论 —— html5ever 支持脚本暂停/恢复与 `document.write` 插入点，但驱动层必须自建

- 状态：**已接受**（PoC 实测 5/5 断言通过）
- 日期：2026-10-12
- 关联：`docs/TASKS.md` 的 T2.3
- 探针源码：`poc/t2_3_html5ever_pause/src/main.rs`
- 运行方式：`cd poc/t2_3_html5ever_pause && cargo run`

## 问题

技术方案 T2.3 要求验证：`html5ever` 能否支持「脚本暂停、恢复与 `document.write` 插入点」，
并明确警告**不能只用一次 `parse_document` 全量解析**（否则无法在 `<script>` 处暂停）。

## 实测方法

不使用 `parse_document`，而是直接驱动低层 `Tokenizer` + 自定义 `TokenSink`：
把 HTML 切成 [前缀] / [script 段 + 后缀] 两段分别 `feed`；在 sink 里对 `<script>` 与 `</script>`
作特殊处理；观察 `feed` 的返回值，从而确认是否存在暂停点、恢复后状态是否正确。

## 关键发现（全部为实测原文，非推断）

### 1. raw-text 状态**不由 Tokenizer 自动进入**

初版探针的 sink 一律返回 `TokenSinkResult::Continue`，结果 `<script>` 体内的 `<b>`
被当成真实标签产出：

```
FINAL_TOKENS = [..., "START(script)", "TEXT(var x = \")", "START(b)", "TEXT(not-a-tag)",
               "END(b)", "TEXT(\";)", "END(script)", ...]
ASSERT_FAIL(b): <script> 内的 <b> 被误解析为标签
```

即：**只驱动 Tokenizer 而不通知状态切换，`<script>` 语义就不成立。**

### 2. `TokenSinkResult` 有四个变体，sink 可主动改状态

`html5ever-0.27.0/src/tokenizer/interface.rs:73-80` 原文：

```rust
#[must_use]
pub enum TokenSinkResult<Handle> {
    Continue,
    Script(Handle),          // 要求暂停，把脚本节点交还驱动层
    Plaintext,
    RawData(states::RawKind) // 进入 Rcdata / Rawtext / ScriptData 状态
}
```

`tokenizer/mod.rs:443-457` 显示 sink 的返回值直接驱动状态机：

```rust
match self.process_token(token) {
    TokenSinkResult::Continue => ProcessResult::Continue,
    TokenSinkResult::Plaintext => { self.state = states::Plaintext; ... },
    TokenSinkResult::Script(node) => { self.state = states::Data;
                                       ProcessResult::Script(node) },
    TokenSinkResult::RawData(kind) => { self.state = states::RawData(kind); ... },
}
```

### 3. 暂停点真实存在，且可恢复

`TokenizerResult<Handle>` 为 `{ Done, Script(Handle) }`。sink 在 `</script>` 处返回
`TokenSinkResult::Script(())`，`feed` 随即返回 `Script`，此时 tokenizer 状态被置回
`states::Data`，驱动层再次 `feed` 即可恢复：

```
SCRIPT_PAUSE #1 → 执行脚本，document.write 注入内容
ASSERT_PASS(c): </script> 处产生 1 个暂停点 —— TokenSinkResult::Script 生效
ASSERT_PASS(e): 恢复后 </script> 后的 <i> 正常解析 —— tokenizer 回到 Data 状态
```

### 4. **`push_back` 是错的** —— 插入点语义的关键坑

第一版把脚本产出 `push_back` 到 `BufferQueue` 末尾，注入内容被排到了**整段输入的末尾**：

```
FINAL_TOKENS = [..., "END(script)", "START(i)", "TEXT(after)", "END(i)",
               "END(p)", "END(body)", "END(html)", "START(u)", "TEXT(written-by-script)", "END(u)"]
```

即「解析到文档结束后才插入」，**不符合插入点语义**。改为 `push_front` 后正确：

```
FINAL_TOKENS = [..., "END(script)", "START(u)", "TEXT(written-by-script)", "END(u)",
               "START(i)", "TEXT(after)", "END(i)", "END(p)", "END(body)", "END(html)"]
```

脚本产出落在 `</script>` 与 `<i>` 之间——这才是 `document.write` 应有的位置。

### 5. html5ever 自带 driver **未实现**该语义（自认 FIXME）

`html5ever-0.27.0/src/driver.rs:106-110` 原文：

```rust
fn process(&mut self, t: StrTendril) {
    self.input_buffer.push_back(t);
    // FIXME: Properly support </script> somehow.
    while let TokenizerResult::Script(_) = self.tokenizer.feed(&mut self.input_buffer) {}
}
```

它把 `Script(_)` 直接丢弃并继续喂，**既不暂停也不执行脚本**。因此
`parse_document` 无法直接满足需求——技术方案的担心是对的。

## 结论

**可行**，但驱动循环必须由 `navigation` crate 自己实现，四步缺一不可：

1. sink 对 `<script>` 起始标签返回 `TokenSinkResult::RawData(RawKind::ScriptData)`；
2. sink 对 `</script>` 返回 `TokenSinkResult::Script(handle)` 产生暂停点；
3. 驱动层在暂停点**执行脚本**，并把 `document.write` 的产出用
   **`push_front`** 插入输入队列（不是 `push_back`）；
4. 脚本执行完毕后**再次 `feed`** 恢复解析。

### 附带的 API 约束（写代码时会踩）

| 约束 | 说明 |
|---|---|
| `Rc<RefCell<S>>` **不是** `TokenSink` | sink 必须**按值**交给 `Tokenizer`；共享日志要用 `Rc<RefCell<Log>>` 单独克隆 |
| `BufferQueue::new()` 不存在 | 用 `BufferQueue::default()` |
| `BufferQueue` 只有 `is_empty()` | 没有 `len()` |
| `Token` 需覆盖 `EOFToken` | 少了会 `E0004` non-exhaustive |

## 对 `navigation` crate 的设计约束（须遵守）

- 解析驱动**不得**封装成「一次性 `parse_document`」的薄封装；必须是可暂停/可恢复的循环。
- 「脚本执行」与「输入注入」是**两个独立关注点**：前者属 `scheduler`，后者属 `navigation`；
  插入点以 `push_front` 表达，不得由上层直接操纵 `BufferQueue`。
- 插入点顺序（发现 4）必须写成**回归测试**，否则任何「简化队列操作」的改动都会静默破坏
  `document.write` 语义。
