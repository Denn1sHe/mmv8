## 决策 D1：句柄表与 GC 纪律

### D1.1 我的独立结论（与 brief 推荐**不同**）

**不采纳 brief 推荐的「纯方案 B（全弱槽 + 显式租借）」；采用「强引用槽表 + 独立弱句柄通道」的修正方案**，
即：施工图 §1.2 的槽表示（强）+ abi.rs 已有的 `WeakJsHandle`（弱），但必须**修正施工图内部矛盾**（见 D1.5）。
可执行要点：

1. `Slot { generation: u32, value: Option<v8::Global<Value>> }`（**强**）；`free`/`drain` 释根；
   `generation` 单调递增做复用防呆 —— 直接兑现 techplan §5 line154「节点池复用也不能让旧句柄指向新节点」。
2. **另设 `WeakJsHandle`**（`v8::Weak<Value>` 的安全影子），**仅** DOM 面 / `node_map` / 监听器槽使用；
   `web-dom`/`web-events` 类型面**不得**出现 `JsHandle`（C-2）。
3. **删除或降格 `HandleLease`**：不得作为「安全机制 / 防环」叙事（理由见 D1.3-2）；若保留，仅作
   「作用域内显式释放」的人机接口，并在注释写明「**不**防跨语言环」。
4. §3.4 测试 `handle_not_a_gc_root` **改写**：仅持 `WeakJsHandle` ⇒ GC 后可回收；
   仅持 `JsHandle`（强槽）⇒ 存活 —— 这才是 A 的真实语义。

### D1.2 三条决定性理由

1. **brief 的头号理由「方案 A 与 C-1 字面冲突」不成立。** C-1 原文（ADR-0009 决策 5）约束的是
   **`JsHandle` 这个类型本身的实现**：「其实现只能是 slot table 的下标…**不得**是 `v8::Global` 的包装」，
   其可判定判据是「`JsHandle` 的 impl 中禁止出现 `Global::new`」。方案 A 下 `JsHandle` 仍是
   `u64` 下标，`Global::new` 在 `HandleTable::alloc`，**不在 JsHandle impl**。⇒ A **字面满足 C-1**。
   brief「§3 方案 A – 缺点」第一句「与 C-1 的**字面**冲突」系**误读**，B 的推荐据此塌陷。
2. **brief 的「B 让强引用环在类型层面难构造（C-4）」是跨层错配。** ADR-0007 实测的泄漏是
   「cppgc 宿主对象 ↔ V8 闭包」的**跨两堆环**，不是「两个 Rust lease 互相捕获」的 Rust 所有权环；
   `HandleLease` 不 `Clone`/不 `Copy` 只能防**后者**，对 ADR-0007 的威胁模型**无效**。真正的防环机制是
   **C-2（DOM 面不得出现 JsHandle）+ 单向设计**（ADR-0007「对架构的直接影响 1」），**与 A/B 正交**。
3. **B 用「不可判定失败」换「结构性防误用」，与铁律 10「不静默降级」相冲。** 弱槽下 `eval` 返回的
   值在两次调用间可能被**静默回收**（施工图 §7 未确定点 2 自认），须再加「默认租借」才可用；
   加了「默认租借」后 **B ≈ A 但更复杂**。而 A 的过度保留是**确定性、可诊断**（内存增长可见、
   可用显式 `free`/`drain` 收敛）。⇒ 在 G1 阶段选 A 是更稳的工程取舍。

### D1.3 自我攻防

- **对我结论最强的反例**：techplan §5 line155 白纸黑字「**仅靠…全局 Persistent 表会泄漏
  『节点 → 监听器 → 闭包 → 节点』循环**」。我的「强引用槽表」正是「全局 Persistent 表」；
  若让它承载监听器闭包，就**正中此警告**。**回应**：该警告针对的是「用持久强表承载 DOM↔监听器边」。
  我的修正方案把该边**强制走 `WeakJsHandle`**，强表只承载**不参与跨语言环**的值。故 A 与 §5 **可兼容**，
  但**前提是把「监听器/节点映射一律弱」写成硬条款 + 门禁**（否则 A 会因纪律松被误用）。
- **会改变我结论的证据/实验**：① 若实测证明「B + 默认租借」能让返回值意外率≈0 且成本可控，
  B 的**结构性免疫误建环**可能反超 A；② 若 G4 的 `SharedIsolate` 成为默认，B 更受限（F3）。
- **我未能完全证伪 B**：B 的「**无任何强句柄 ⇒ 不可能误 pin 成环闭包**」这一**结构性优点**，
  我没能攻破；我只证伪了它**给出的理由**。故我的结论是「**A 为主 + 弱通道**」，而非「A 全面胜出」。

### D1.4 被拒方案残余风险（供登记）

- **方案 B（纯弱槽）**：① 返回值静默失效（不可判定）；② `v8::Weak` 在 shared isolate 上 assert 失败
  （F3）⇒ G4 Worker 路径天然受限；③ 弱槽回收往往需 GC 终结回调，而终结回调**不得进 Python/JS**
  （F4 + techplan §6 line156）⇒ 与铁律相冲。
- **方案 A（强槽）**：若 C-2 门禁失效、有人把**捕获 DOM 的闭包**强登记进表 ⇒ 复现 ADR-0007 泄漏。
  ⇒ 必须由门禁 + 「node_map/监听器一律弱」条款兜底，**不能只靠人自觉**。

### D1.5 施工图必须修的内部矛盾（高优先）

1. **槽表示 vs C-1 测试互相矛盾**：§1.2 `Slot{ value: Option<v8::Global> }`（**强**）与
   §3.4 `handle_not_a_gc_root`「仅持 `JsHandle`（弱路径）…可回收」**不可能同真**（强槽下持句柄即存活）。
   **必须二选一**，否则工程师照施工图写必然撞墙。
2. §1.2 `HandleLease` 注释「只有持有一个 `HandleLease` 才保证对应 JS 值存活」在**强槽**表示下**为假**
   （槽本身已 root，lease 是空转）。
3. §1.2 `node_map` 用 `JsHandle`（强）与 C-2 / techplan §5 相冲 ⇒ `node_map` 应持**弱**句柄。

## 决策 D2：PyO3 回调派发

### D2.1 我的独立结论（主问题与 brief **同向**；子问题 3 **反向**）

- **主问题（派发）**：采纳**方案 A（同线程直呼）**，但须补一个**硬前置**并**修订 ADR-0012 字面**：
  `eval` **全程持有 GIL**（不得 `allow_threads` 包住 V8 运行）；回调派发**不跨线程抢 GIL**。
- **子问题 3（unsafe 归属）**：**否决 brief 推荐的方案 C（把 PyO3 边界移进 engine-v8）**。
  U-1 已决（F6）⇒ sdk-python **直接持有 PyO3**，**不改白名单、不改 ADR-0009 决策 2**。
  移进 engine-v8 反而**扩大 unsafe 面**且**与 ADR-0009 决策 2 字面冲突** —— 这是**制造回归**。

### D2.2 三条决定性理由

1. **U-1 已决（证据 F6）使 brief 的 §6「首选方案 C」成为过期建议。** 反向注入（p1c_armed）证明
   lint 武装有效，故「PyO3 宏会不会撞 forbid」的答案 = **不撞**；「是否需要移边界」的问题**不存在**。
   采纳方案 C 会无收益地把 PyO3 拉进白名单 crate ⇒ 违背 ADR-0009「白名单不变」。
2. **方案 A 结构性消除 ADR-0012 的死锁路径。** ADR-0012 条件表：`TIMEOUT` **仅**出现在
   `spin_holding_gil`（**另一线程**持锁忙等），而同组 `sleeping`/`not_holding` 均 `CLEAN_RESUME`。
   方案 A 下调用线程**已持 GIL**、无第二个 Python 线程、无跨线程 acquire ⇒ 互等前提**不存在**
   （不是「没测出来」，是「没有这条路」）。
3. **方案 B（attach/detach 异步）在 G1 超范围且未实测。** ADR-0012 遗留明写「`attach`/`detach`
   异步化方案**需另起 PoC 验证**」；且它把「JS 同步调用宿主」语义改成异步。⇒ 登记为 **G4**。

### D2.3 自我攻防

- **对我结论最强的反例**：ADR-0012「对架构的直接影响 1」**字面**要求「**必须**使用 PyO3 的
  `attach`/`detach` 语义」。方案 A **不用** attach/detach ⇒ **字面抵触**。**回应**：该条**目的**是
  「不在页面线程同步获取 GIL 等待」，A 满足**目的**但不满足**字面**。因此我**要求修订 ADR-0012**，
  把该条限定为：「**仅当回调入口线程不持 GIL（暂停泵 / 跨线程）时**才必须 attach/detach；同线程再入豁免」。
  **不做此修订，A 就是「无 ADR 依据的执行」**（违铁律 6「先落 ADR 再写代码」）。
- **A 的真实代价**：`eval` 全程持 GIL ⇒ **阻塞所有其他 Python 线程**。必须写进 ADR，不得隐瞒。
- **回调截止期限 A 无法抢占式兑现**：techplan §6 line186 要求「同步宿主回调必须有截止期限」。
  若 Python 回调自身阻塞（等锁/`sleep`），它持 GIL 在**本线程**跑，watchdog 的 `terminate_execution`
  打的是「正在 V8 里执行的 JS」，**打不到 CPython**（ADR-0012 主结论）⇒ **无界挂起**。
  **会改变我结论的证据**：若实测存在「跨线程可中断 CPython（信号 / `settrace`）」的可行路径，则可升级为
  强截止期限；否则 G1 只能「协作式」。**我给出的可执行兜底**（三选一或组合）：(a) 契约强制回调
  **不得阻塞**并写入文档；(b) 运行时**计量**宿主侧墙钟，超限后该 Realm 后续操作一律报
  `Terminated`/`Deadline` 并 `close`（**事后**可判定，非抢占）；(c) 登记「阻塞回调导致页面线程无界挂起」
  为**已知局限**，G4 用 attach/detach 异步通道根治。
- **重入禁令（Q3）仅靠 `Realm.in_callback: bool` 不够**：必须让该标志在**所有**入口
  （`eval`/`eval_module`/`call`/`perform_checkpoint`/**微任务执行**）被检查，且由**回调 trampoline**置位；
  否则「微任务内调 native fn 再 `eval`」可**静默绕过**（ADR-0012 D5 已证重入**不崩**，故绕过是静默的）。

### D2.4 被拒方案残余风险

- **方案 C（PyO3 移 engine-v8）**：扩大 unsafe 白名单面；与 ADR-0009 决策 2 冲突；需改 ADR；且**不必要**（F6）。
- **方案 B（异步 attach/detach）**：未实测；把 JS 同步语义改异步；G1 超范围。
- **方案 A 残余**：阻塞式 Python 回调 ⇒ 页面线程**无界挂起**（不可被 watchdog 打断）；全程持 GIL 阻塞其他 Python 线程。

## 剩余不确定点（交主理人 / 工程师实测）

1. `v8::Weak::to_local` 在 GC 后返回 `None` 的确切行为，需最小实测（沿 T2.1 的 `WeakRef` 判定法）。
2. 方案 A 下「`eval` 全程持 GIL」对并发 Python 线程的实际阻塞表现，需一条可判定测试。
3. 是否存在跨线程可中断 CPython 的可行路径（决定 D2 截止期限是抢占式还是协作式）。
4. 反向注入：`engine-v8` 内 `pub use` 类型别名绕过门禁规则 5（ADR-0009 已登记盲区）——建议 QA 复核该盲区是否被新增。
