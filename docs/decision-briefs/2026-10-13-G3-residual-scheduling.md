## 0. 一句话问题

> **G2 留了四个「已登记、非缺陷」的残留项：① 脚本没有任务化（在页面加载里同步跑）；② 没有定时器
> （timer）驱动的事件循环；③ 模块脚本没接上「超时看门狗」；④ 部分宿主路径没换成「非 panic 的借用」。
> G3 以布局为核心——这四个残留项，**哪些必须挪进 G3 一起做，哪些可以继续推到 G4**？**

## 1. 背景与上下文

- **这个仓库是什么**：`iv8` 是**自研浏览器运行时**。它有「页面加载 → 解析 → 跑脚本 → 事件循环」的
  基本骨架（G2 已完成），现在进入 G3（**样式/布局/几何**）。
- **涉及模块 / 文件路径**：
  - `crates/scheduler/`（事件循环 / 任务泵 / 时钟）
  - `crates/navigation/src/page.rs`（`BrowsingContext`：把解析、绑定、调度串起来）
  - `crates/navigation/src/parser.rs`（脚本执行）
  - `crates/engine-v8/`（V8 桥，含 `try_borrow` 借用纪律）
- **四个残留项的准确含义**：
  - **U-10**：G2 的「执行模型 as-built」——**阻塞脚本在页面加载（`load`）里同步执行**
    （带 2 秒超时），而不是作为「任务」进入事件循环排队。**延期项**：① 脚本任务化；② timer 事件循环。
  - **U-12**：**模块脚本的求值没有接上「超时看门狗」**——模块里的死循环**不受** 2 秒截断。
  - **D4 残余**：**宿主驱动路径**（`load`/`run_until`/`pump_fetch`/`resolve_completed`/`close`）
    没有从「可能 panic 的借用」换成「返回可判定错误的借用（`try_borrow`）」；而所有 **V8 回调边界**
    （30 处）**已覆盖**。
- **为什么现在讨论**：G3 要新增「DOM 变更 → 重新布局」的路径，**会触及宿主驱动路径的借用**；
  且「布局失效」的真实触发源之一就是**定时器**。所以这四个残留项与 G3 的耦合度需要**判断**。

## 2. 需要拍板的问题

- **主问题**：四个残留项（脚本任务化 / timer 事件循环 / 模块 watchdog / 宿主 `try_borrow`）
  各自的**归属**（G3 还是 G4）？
- **子问题**：
  1. G3 的「动态失效」测试**能否只用同步脚本 + 显式重算**完成？（若能 ⇒ timer 事件循环可推后）
  2. G3 是否会跑「模块内死循环」？（若不会 ⇒ 模块 watchdog 可推后）
  3. G3 新增的 `resolve`/几何路径**是否跨 V8 回调边界**？（若不跨 ⇒ 宿主 `try_borrow` 可推后）

## 3. 备选方案（至少两个）

### 方案 A：**全部推 G4**（G3 只做样式/布局/几何/字体/Shadow）

- **做法**：四个残留项一律登记为 G4；G3 的失效测试用「**同步脚本改样式 + 显式 `resolve`**」。
- **关键代码**（原文 —— G3 失效测试的形态，不依赖 timer）：
  ```rust
  let mut m = tree.borrow_mut();
  m.set_attribute(class_box, "class", "big");   // 同步改，无 timer
  drop(m);
  page.resolve_now()?;                          // 显式重算（释放可变借用后）
  let w = backend.geometry(class_box)?.offset.width;
  assert_eq!(w, 300.0);
  ```
- **优点**：G3 范围最小、聚焦布局；四个残留项在 G4 作为「执行模型收口」一起做更内聚。
- **缺点与风险**：① 若 G3 需要「异步（timer 触发）布局变更」的真实场景 ⇒ 缺失；② 模块 watchdog
  继续缺口（安全面）。
- **长期影响**：G4 承担「执行模型收口」。
- **预估工作量**：小（G3 侧）。

### 方案 B：**timer 事件循环 + 模块 watchdog 归 G3；脚本任务化 + 宿主 `try_borrow` 归 G4**

- **做法**：G3 补「定时器驱动的事件循环」与「模块求值接 watchdog」；其余两项推 G4。
- **关键代码**（原文 —— as-built 延期项原文，`docs/design-g2-page-2026-10-13.md:1149-1151`）：
  ```
  - **执行模型（as-built，批 2G）**：阻塞脚本在 `load` **内同步执行**（`eval_with_deadline`，上限固定 2 s）；
    `run_until` 驱动 **网络/MO/输入** 任务泵 + 微任务检查点。**延期项（登记，非缺陷）**：
    ① 脚本任务化（`ScriptBlocking` 队列）；② timer 驱动的页面事件循环。
  ```
- **优点**：① timer 是「动态失效」的自然触发源之一，G3 有它更完整；② 模块 watchdog 修补一个
  **安全缺口**（死循环），与「G3 引入大量新代码」叠加时更该补。
- **缺点与风险**：① timer 事件循环触及 `scheduler`（**铁律 6 高风险路径** ⇒ 须走决策上报）；
  ② 范围扩大。
- **长期影响**：G3 体量增大；G4 只剩「脚本任务化 + 宿主借用」两件小事。
- **预估工作量**：中。

### 方案 C：**四项全进 G3**

- **做法**：四个残留项全部在 G3 补完。
- **优点**：执行模型一次性收口。
- **缺点与风险**：① 脚本任务化与布局**无直接耦合**，进 G3 会稀释「布局复用验证」的主题；
  ② 触铁律 6 与 ADR-0017 as-built 注记，回归面大。
- **长期影响**：G3 名实不符（变成「执行模型收口」）。
- **预估工作量**：大。

## 6. 本代理的推荐（**仅供参考**）

- **推荐：方案 B（timer 事件循环 + 模块 watchdog 归 G3；脚本任务化 + 宿主 `try_borrow` 归 G4），
  但标注为「若 S1 探针证明 G3 失效测试全可同步完成，则降级为方案 A」。**
- **理由**：
  1. **timer 事件循环**：G3 的「动态失效」在真实页面里**常由定时器触发**（如 `setTimeout(()=>el.style…, 0)`）；
     有它可让失效测试**更接近真实**。**但它触铁律 6 ⇒ 必须先落 ADR**（本 brief 即上报）。
  2. **模块 watchdog（U-12）**：这是**安全缺口**（模块内死循环不截断），G3 引入大量新代码时更该补。
  3. **脚本任务化**：与布局**无直接耦合**（G2 已用同步脚本覆盖），推 G4 合理。
  4. **宿主 `try_borrow`**：ADR-0016 已裁定「非 V8 回调边界、冲突面小」且 G3 的 `resolve` 同性质
     ⇒ **风险不因 G3 放大**，推 G4 合理。
- **我不确定的点**：
  1. **timer 事件循环是否真的「G3 需要」**——若 G3 全部失效测试可同步完成，则它其实可推 G4
     （⇒ **取决于 S1/S4 的失效测试形态**）。我倾向「**先按需**」：G3 若某条失效测试非 timer 不可，
     再补，而不是预先做。
  2. **模块 watchdog 的实施成本**（接 `eval_with_deadline` 到 module eval 的路径）是否小到可进 G3。
  3. 是否需要把「执行模型收口」**单列一个 G4 子闸门**（避免 G4 变杂）。
