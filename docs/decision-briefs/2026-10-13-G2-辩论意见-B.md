## 1. 我的独立作答（写在读 brief 之前的位置）

> 说明：本节是我只读技术方案 / ADR / 源码后给出的结论与理由。为避免事后合理化，
> 我保留了我认为**最不确定**的点，便于与 brief 对照时暴露分歧。

### D1 —— DOM 内核数据结构与所有权

**结论**：**扁平 arena（`Vec<Option<NodeData>>` + 每槽 generation）+ 不透明 `NodeId(u64)`**。
`NodeId` 打包与 `engine_v8::JsHandle/WeakJsHandle` 一致（高 32 generation / 低 32 下标），
`node_map` 直接用 `id.raw()` 作 u64 key。DOM 侧**不持任何 JS 引用**。

理由（挂证据）：
1. 技术方案 §5（docx 行 154）原文：*「DOM 用带 generation 的 NodeId 标识节点……**节点池复用也不能让旧句柄指向新节点**」* ⇒ generation 是硬要求，`Rc<RefCell<Node>>`（方案 B）在类型上给不出。
2. 技术方案 §5（行 155）说「**首选**验证 cppgc 跨堆追踪……若绑定缺少必要接口，补小型 C++ tracing 桥」，但 **ADR-0007 已实测 `v8` crate 未暴露 `TracedReference`**、跨堆环无法回收 ⇒ 「补桥」是铁律 6 高风险且本轮不做，故只能选「DOM 侧不持 JS 引用」的单向形态。arena 天然满足。
3. 与 G1 `HandleTable`（弱槽 + generation，`handles.rs`）**同构**，全仓一套心智。

**我认为最不确定的点**（读 brief 前）：
- 「不重入」是本方案唯一的运行期安全依靠吗？我的判断：**它不够**。技术方案 §7（行 189）自己写的是
  *「遇到需要执行的脚本，解析暂停，**释放 DOM 可变借用后交由 V8 执行**」* ——这是**明文要求**，
  不是可选纪律。而施工图把它降级成 R4 的一条「对策：纪律」。本仓对「退回纪律」的形态是否决级的
  （ADR-0009 决策：「类型系统层面的保证，而非纪律层面的保证」；ADR-0013 决策 7.3 以「**退回纪律 + 门禁**」为否决理由）。
- 「节点删除 = 只脱离树、不回收槽」我同意；但**槽回收 API 在 §1.2 根本不存在**（`NodeTree` 无 `remove`/`dispose`），
  那 generation 复用这条卖点的**测试无从写起**。

### D2 —— 解析器宿主 + 执行协议 + 调度器核心（含子问题 4）

**结论**：**任务化（方案 A）** + 单线程消息泵。但我要把 brief 的 A 拆成两件**互相独立**的事：
「脚本执行是否入队」= 是（为了与 network/timer/input 同一模型、为了 `run_until` 语义明确）；
「脚本执行是否**可被预算打断**」= **任务化并不能回答这个问题**。

理由：
1. ADR-0006 明文分工：「脚本执行」属 `scheduler`、「输入注入」属 `navigation`，插入点用 `push_front`，
   **上层不得直接操纵 `BufferQueue`** ⇒ 方案 B（就地同步）与 ADR-0006 的分工表述冲突。
2. §16（行 410）「**禁止 eval 悄悄无限等待**」+ §6（行 175）「预算：task 数、总 CPU/墙钟……**支持中断**」
   ⇒ 需要任务边界，故 A。
3. **U-1 我自己核了源码（未依赖 brief 的「待实测」）**：
   - `html5ever-0.27.0/src/tree_builder/rules.rs:745-747`：`Text` 模式下遇 `</script>` 结束标签
     `let node = self.pop(); ... return Script(node);`
   - `tree_builder/mod.rs:371-373`：`Script(node) => return tokenizer::TokenSinkResult::Script(node);`
   - `tokenizer/mod.rs:449-457`：`TokenSinkResult::Script(node) => { self.state = states::Data; ProcessResult::Script(node) }`，
     并经 `:368/:376` `return TokenizerResult::Script(node)`。
   ⇒ **U-1「成立」是源码级确定**，风险等级应从「待实测」降为「已在源码层证实，S8 只做回归确认」。
   - `<script>` 起始 → `RawData(ScriptData)`：`tree_builder/mod.rs:245`（`scripting_enabled=true`）。
4. `BufferQueue::push_front` 确实存在（`markup5ever-0.12.1/util/buffer_queue.rs:78`，
   `markup5ever` 的 `BufferQueue`；无 `new`，有 `is_empty`，与 ADR-0006 的 API 约束一致）⇒ U-5 成立。

**我认为最不确定的点**（读 brief 前）：
- 「任务化」是否真的能给「脚本执行」上预算？我的判断：**不能**。`max_tasks`/`deadline` 是**任务之间**的检查，
  而一个 `ScriptBlocking` 任务内部同步 `Realm::eval` 一个死循环脚本 ⇒ `run_until` 无界。G1 只有
  `perform_checkpoint` 有 watchdog + `terminate_execution`（`realm.rs:489-527`），`eval` **没有**
  （`realm.rs:205-258` 无 watchdog）。这是我读 brief 前就认定的**头号缺口**。
- 调度器「任务源分队列」的**跨源选择顺序**：`BTreeMap<TaskSource, VecDeque<_>>` 按 enum 顺序
  （Timer→Network→UserInput→Message→Microtask→ScriptBlocking），但 §6 只说「源内保持规定顺序」，
  **没有定义源间顺序**。跨源顺序是**可观测**的（timer vs 早期 network complete）。
- 逻辑时钟：§6「逻辑模式按调度事件跳转，**不实际等待**」；但设计里 `Clock::advance` **没有任何调用者**，
  Python 面（§2.7）也没有 advance/sleep 接口 ⇒ logical 模式下 `setTimeout` **永远不会触发**。

### D3 —— 资源等待与导航

**结论**：**方案 A**。`run_until` 返回 `WaitingIo` 逐字兑现 §6（行 185「缺少在线响应时返回 waiting_io，
**不凭空完成请求**」）与 §16。`network.complete` 只入队、由 `run_until` resolve（满足 ADR-0014）。
epoch 作废把「旧响应不写新页面」变成**可判定校验**。

理由：技术方案 §4（行 147）「新导航撤销旧文档任务和资源消费者，**延迟返回的旧响应不能写入新页面**」；
§9（行 218）「资源未命中进入**等待或明确失败**；允许宿主稍后注入」。

**我认为最不确定的点**（读 brief 前）：
- 「导航」到底改了什么？§4 说「撤销旧文档任务」，但设计里 `PageShared.tree: Rc<RefCell<NodeTree>>`
  被 `ParserHost` / `DomSink` / `PageBinding` / `PageShared` 多方 clone 持有。`begin_navigation` 的签名
  只动 `url/readyState/blockers/epoch`，**不动树**。那新文档的 `NodeTree` 从哪来、旧 holder 怎么重绑？
  时序图只画了 `begin_navigation` + `abort_epoch`，没画「重建 DOM / 清 node_map / 清 registry」。
- `__iv8_fetch` 是 `NativeFn`（签名 `&mut Realm`，见 `realm.rs:26` / `native_fn.rs`），它需要够到
  `NetworkService` 和「res/rej 的 `HandleLease` 表」。**闭包能捕获什么？** 设计和时序图都没说这张表住哪。
- epoch 只挂在 network 上；§4 明说「每个异步请求、**句柄、Worker 和日志条目**」都带 epoch，
  那 timer / input 任务怎么带？（`TaskToken` 是 opaque u64。）

### D4 —— 输入最小模型（聚焦）

**结论**：**方案 A（显式 target 可信事件，命中测试推 G3）**。证据：技术方案 §7（行 196）「坐标输入从
命中测试确定目标，**显式 target 输入则验证节点仍属于当前 Document**」+ 施工图几何 stub 口径
⇒ 显式 target 是**规范明文允许**的最小面，命中测试在 stub 几何下做等于**假绿**（违反
`docs/HANDOFF-2026-10-12.md` §六.5「不假绿」纪律）。

**我认为最不确定的点**（读 brief 前）：
- `web-events` 里 `Event` 是纯 Rust struct，`plan_dispatch` 是纯函数；那 **JS 侧监听器读到的 `event`
  是什么对象？** `event.isTrusted` / `event.currentTarget` / `event.type` 谁写进去？§1.2 **没有任何桥的签名**。
- 规范要求「监听器变更」有语义（§7 行 195：「……**监听器变更**」）。`plan_dispatch` 生成**快照**，
  那「分派期间移除尚未调用的监听器」要不要生效？
- `el.click()`（脚本内触发）会走 `Realm::call(listener)`，而 `Realm::call` 在 `in_callback==true` 时
  报 `ReentrantEval`（`realm.rs:344-349`）⇒ **脚本内同步 dispatch 会被自己的重入禁令挡住**。

## 3. 机制走查断链清单

> 走查路径：Python(`sdk-python`) → `BrowsingContext`(navigation) → `ParserHost`/`RunLoop` → `Realm`(engine-v8)
> → `NodeTree`(web-dom) / `web-events` → 回 Python。逐跳问：**谁在什么时刻持有谁的借用？重入窗口在哪？错误在哪断？测试观察点是否存在？**

### 断链 1（D2/D3 · crate 依赖环，2 条）——**阻断**

- **环①**：`scheduler::TaskExecutor::run_task(...) -> Result<TaskVerdict, **PageError**>` 与
  `RunLoop::run_until(...) -> Result<RunOutcome, **PageError**>`（施工图 §1.2「scheduler」块；D2 brief §3、D3 brief §3 同款）。
  `PageError` 是 `navigation::error::PageError`（§1.1）。而 `navigation::BrowsingContext` 又持
  `runloop: scheduler::RunLoop` ⇒ **`navigation ↔ scheduler` 双向依赖**，Cargo 直接拒绝。
- **环②**：`network::RequestSpec { ..., epoch: **NavigationEpoch**, ... }` 与
  `NetworkService::abort_epoch(NavigationEpoch)`；`NavigationEpoch` 定义在 `navigation`（§1.2）。
  而 `navigation::PageShared { network: network::NetworkService }` ⇒ **`navigation ↔ network` 双向依赖**。
- 现状证据：所有相关 crate 的 `[dependencies]` 目前为空（我 `cat` 确认），依赖方向**尚未确定**，
  因此这两条环是**设计引入**、尚未被任何门禁发现。
- 修法（择一）：① `scheduler` 自持 `SchedulerError`，`PageError: From<SchedulerError>`；
  ② `NavigationEpoch` 下移 `policy`（navigation/network 都依赖它）或 `network` 侧只收 `u64`；
  ③ trait 返回值改为 `Result<TaskVerdict, Box<dyn std::error::Error + Send + Sync>>`（不推荐，丢类型）。

### 断链 2（D2 · §1.2 ↔ §2.7 自相矛盾，`ControlPlane` 归属）——**阻断**

- §1.2：`pub struct BrowsingContext { **realm: engine_v8::realm::Realm**, shared, runloop, binding }`
  且 `fn realm_mut(&mut self) -> &mut Realm`。
- §2.7：*「`PyContext` 由「持 `ControlPlane`」升级为「持 `BrowsingContext`（**内含 `Realm` 经 `ControlPlane`**）」*；
  §2.1 第 4 步：*「在**页面 scope（`ControlPlane::with_page_script`）**下 `Realm::eval`」*。
- 源码事实：`PyContext { plane: RefCell<ControlPlane> }`（`sdk-python/src/lib.rs:80`），
  `ControlPlane { realm: Realm }`（`control.rs:26`）、`ControlPlane::with_page_script`（`control.rs:70`）、
  `eval_control` 撤 `__iv8__`（`control.rs:47-59`）。
- 冲突后果：按 §1.2 直持 `Realm`，则 `with_page_script` 无从调用 ⇒ **`ControlRevoked` / `inline_script_runs_in_page_scope`
  无法实现**（G1 已验收的能力在 G2 丢失）；按 §2.7 持 `ControlPlane`，则 §1.2 签名错。
- 这正是 G1 抓到过的**「A/B 混写」同款**。修法：`BrowsingContext` 字段改 `plane: engine_v8::control::ControlPlane`，
  `realm_mut()` 经 `plane.realm_mut()` 转发，脚本任务体走 `plane.with_page_script(...)`。

### 断链 3（D2 · `ParserHost` 无归宿）——**高**

- §2.1 要求 `BrowsingContext` 驱动 `ParserHost`（`feed`/`enqueue_document_write`/`resume`/`finish`），
  但 §1.2 的 `BrowsingContext { realm, shared, runloop, binding }` 与 `PageShared { controller, tree, style,
  registry, activation, network, mutations }` **都没有 `parser` 字段**。
- `ParserHost::new(tree: Rc<RefCell<NodeTree>>, opts)` 与 `ParserHost::finish(**self**)`（按值消费）
  ⇒ 生命周期/所有权未定。谁来 drop / replace 它（导航时）也没有落点。
- 测试观察点影响：`blocking_script_pauses_parser` / `script_executes_then_resumes` 需要**从测试直取**
  `ParserHost` 的 `feed` 返回值——若它住在私有字段里，观察点存在但路径未定义。

### 断链 4（D3 · 导航替换文档/树的重绑）——**阻断**

- 时序图第 22 行 `BC->>DOM: new Document + NodeTree`：导航**新建**树。
- 但 `Rc<RefCell<NodeTree>>` 被至少 4 处 clone 持有：`ParserHost`（`ParserHost::new(tree,..)`）、
  `DomSink`（`Rc<RefCell<NodeTree>>`）、`PageBinding.tree`（§1.2）、`PageShared.tree`。
  `PageBinding` 还持 `node_map: NodeMap`、`parser_active`、`writes`。
- 替换 `PageShared.tree` 的 `Rc` **不会**更新 `ParserHost`/`DomSink`/`PageBinding` 里各自持有的 clone；
  清空**同一** 树则 `node_map`/`ListenerRegistry`/`MutationBuffer`/`PageBinding` 全部要同步失效，
  否则**旧文档的 NodeId / WeakJsHandle / 监听器残留进新文档**（`trusted_click_dispatches_to_target` 等会误命中）。
- 技术方案 §4（行 147）只说了「撤销旧文档**任务**」，未说「撤销旧文档**对象**」；这是设计与规范的**双缺口**。
- 修法：在 ADR 写明「导航 = 原地清空共享 `NodeTree` + 清 `node_map` + 清 `registry` + 清 `mutations` +
  重建 `ParserHost`」，并给出**一条可观察断言**（如 `stale_document_node_rejected`）。

### 断链 5（D3 · `res/rej` 的 `HandleLease` 表无归宿）——**高**

- §2.5 / 时序图第 53、70 行：`__iv8_fetch(u,res,rej)` 把 `res/rej` 经 `Realm::root` 存为 `HandleLease`
  （按 `RequestId` 索引），`network.complete` 的 Network 任务取出 `res` 再 `Realm::call`。
- `__iv8_fetch` 是 `NativeFn`，签名只有 `&mut Realm`（`realm.rs:26`，`native_fn.rs`）；
  它**够不到** `BrowsingContext`/`PageBinding`（不是 `Rc` 共享），也无法在 `Realm` 里落表
  （`Realm` 字段固定：`handles/native_fns/module_registry/...`，`realm.rs:103-125`）。
- 缺的是：**这张 `HashMap<RequestId, (HandleLease, HandleLease)>` 住哪个 `Rc<RefCell<...>>`，
  且该 `Rc` 必须同时被 `__iv8_fetch` 闭包与 `NetworkService` 完成路径可达**。设计未给 ⇒ 断链。
- 附带：`PageBinding.writes`（§1.2）与 §2.1 第 5 步的 `shared.writes` **名称/归属不一致**（两处引用了不同的容器）。

### 断链 6（D2 · 「任务化 ⇒ 有界」不成立，单任务无界）——**阻断**

- `RunLoop::run_until` 在**任务之间**检查 `max_tasks` 与 `deadline`；一个 `ScriptBlocking` 任务体内
  同步 `plane.with_page_script(|p| p.realm_mut().eval(text))`。若脚本含 `while(true){}`，
  该任务永不返回 ⇒ `run_until` 永不返回 ⇒ 违反 §6 行 175「预算……**支持中断**」与 §16 行 410
  「禁止 eval 悄悄无限等待」。
- G1 的对照事实：`Realm::perform_checkpoint` **有** watchdog + `terminate_execution` + `cancel_terminate_execution`
  （`realm.rs:501-522`，含 `TerminateHandle` 跨线程），但 `Realm::eval`（`realm.rs:205-258`）**没有**。
- 修法（择一）：① 把 G1 的 watchdog 模式复用到 `eval`（新增 `Realm::eval_with_deadline`）；
  ② 显式登记「G2 长脚本不可被 `run_until` 打断」为**具名局限** + `capabilities` 标志 + 一条断言该局限的测试。
  **不得**含糊——「任务化」这个词本身不构成兑付。

### 断链 7（D2 · 外部脚本 blocker ↔ `WaitingIo`）——**高**

- 需求：`<script src>` 未命中 OfflineBundle ⇒ 停在 blocker（§3.2 `external_script_blocks_until_loaded`）。
- 但脚本任务在被 `run_until` 取出后若发现 `Pending`，它**不能** `Requeue` 自旋：队列非空 ⇒
  `RunOutcome::WaitingIo` 的分支（「队列空但 `has_pending_io()`」）**永不满足** ⇒ 只会 `BudgetExhausted`。
- 缺的是**停泊态**：任务被移出队列、登记为「等某 RequestId」，完成时再入队；`is_idle()` 须把「有停泊任务」
  计为「队列空」。`RunOutcome::WaitingIo` 的定义要相应精确化。

### 断链 8（D2 · 逻辑时钟无推进者）——**高**

- `Clock::advance(&mut self, d)`（§1.2）在整个设计中**无调用者**；Python 面（§2.7）无 `advance`/`sleep`。
- logical 模式下 `setTimeout(f,1000)` 的 due 时间永不推进 ⇒ 定时器任务永不 due ⇒ `RunOutcome::Idle`，
  而页面「明明有定时器」。
- §6 行 182「逻辑模式**按调度事件跳转**，不实际等待」需要一条策略：**`run_until` 在队列空时跳到最近的
  due 定时器并执行**（虚拟时间跳转、不 sleep），或**由宿主显式推进**（则须在 Python 面加接口）。
  §4 的 `logical_clock_advance_no_sleep` 只测 `advance` 本身，**测不到集成行为**。

### 断链 9（D4 · JS `Event` 对象桥缺失）——**高**

- `web-events::Event`（§1.2）是纯 Rust 结构；`plan_dispatch` 返回 `Vec<DispatchStep{target,phase,listeners}>`。
- 但 JS 监听器回调形如 `function(e){ if(e.isTrusted) ... e.currentTarget ... }`，需要**一个 JS 对象**。
  §1.2 / §2.3 **没有任何**「Rust `Event` → JS 对象」的构造与逐 step 更新 `currentTarget` 的签名。
- `navigation::input` 具备的 `engine_v8::Realm::new_object/set_prop`（§1.2 增量）**足以实现**，
  但「谁来构造、每步怎么更新、`preventDefault`/`stopPropagation` 怎么回读」**未定义**。
- 后果：`trusted_click_dispatches_to_target`、`untrusted_event_not_trusted` 的断言**写不出来**。

### 断链 10（D1 · 真实 `RefCell` 借用冲突序列 2 条）

> 这两条是**具体调用序列**，不是笼统担忧（任务要求）。

- **序列 ①（MutationObserver 交付期间的回环）**：某个微任务 checkpoint 里，编排层取出
  `PageShared.mutations` 的待交付记录并**在持有 `shared.borrow_mut()` 的状态下**逐个调用观察器 JS 回调；
  回调里 JS 又改 DOM ⇒ `PageBinding` 的 native fn 调 `shared.borrow_mut()` 追加新记录
  ⇒ **`already borrowed: BorrowMutError` 运行期 panic**。
  修法：交付前 `mem::take(&mut shared.mutations)` 把记录**copy-out 成 owned**，释放借用后再回调；
  回调期间新产生的记录留到下一轮。
- **序列 ②（`input.dispatch` 期间的热绑定改动）**：`plan_dispatch(tree, registry, target)` 取
  `&self.shared.borrow().tree` 与 `&...registry`；若实现把 `DispatchStep` 的计算与遍历**写在一个表达式**
  里（借用未显式析构），监听器 JS 里执行 `el.addEventListener(...)`（改 `registry`）⇒
  **`RefCell` 可变借用冲突 panic**。
  修法：`plan_dispatch` **必须**在任何 `Realm::call` 之前把借用释放（其结果 `Vec<DispatchStep>` 已是 owned），
  且**类型上禁止**返回借用 registry 的迭代器。

### 断链 11（D1 · `NodeMap` 复用返回死句柄）

- `NodeMap::bind(node, handle)`（`node_map.rs:28-38`）在已有绑定时**直接返回既有 `WeakJsHandle`**，不校验弱槽是否已空。
- 弱句柄被 GC 回收后（`resolve_weak` → `None` / `Collected`，ADR-0013 T1 已实测）⇒ `wrapper_for`
  会拿到一个**指向空槽的弱句柄**，违反「同一节点复用同一 wrapper」的**可用性**（复用了一个死引用）。
- 修法（写进 ADR）：`wrapper_for` 的复用必须是
  「查 `node_map` → 若中，`resolve_weak` → `Some` 则复用；`None`（`Collected`）则 **`unbind` + 新建 wrapper + `bind`**」，
  并**为这条补一个测试**（现有 §3.7 只测了「两次取回同一个」的非 GC 路径）。

### 断链 12（D2 · 错误传播断点：`PageError` 与 `JsErrorKind` 之间的映射缺失）

- `TaskExecutor::run_task -> Result<_, PageError>`、`RunLoop::run_until -> Result<_, PageError>`、
  `BrowsingContext::run_until -> Result<_, PageError>`，而 `Realm::eval` 报 `JsError(JsErrorKind)`。
- 设计说「G2 新增页面/网络类错误**逐项固定**」（§2.7），但**没有给出** `JsError → PageError` 的映射表，
  也没有新增 `JsErrorKind` 变体与既有「变体可达性矩阵」（`error.rs:71` 的 `ALL_KINDS`，穷举守卫）
  的同步清单。§4 只说「新增变体须同步」。
- 后果：`run_until_returns_outcome` / 页面错误的 pytest 断言**无稳定前缀可依赖**（D3 brief §5 却要求
  「G2 新增页面/网络类错误逐项固定」）。缺一张**映射表 + 变体清单**。

5. `run_until` 对「单任务内长脚本」的中断测试——`eval` 无 watchdog，机制不存在（断链 6）。
6. 导航后「旧文档节点被拒」测试——重绑机制未定义（断链 4）。

## 6. 剩余不确定点（我未能定论，建议 S0/专项实测闭环）

1. **`terminate_execution` 打在 `Realm::eval` 上是否可靠**：G1 只在 `perform_checkpoint` 实测过
   （`realm.rs:501-522` 测试 `microtask_budget_exhaustion`）。把 watchdog 挪到 `eval` 包住脚本任务，
   是否能稳定截断**纯计算**死循环（非微任务递归）？**待专项 PoC**（这决定 B-3 是「接 watchdog」还是「只登记局限」）。
2. **`Weak` 槽回收与 `node_map`/监听器槽的清理时机**：`Weak` 回收**不保证终结回调**（ADR-0007）；
   那 `node_map` 里的死 `WeakJsHandle` 条目**何时**清理？只在 `wrapper_for` 访问时惰性清理，
   还是别处？惰性清理会让 `node_map` 单调增长（长跑泄漏面）。**待定**。
3. **几何 stub 与默认动作的交互**：`click ⇒ 聚焦` 不需要几何，但「焦点」状态在 G2 存哪、
   是否要在 `document.activeElement` 上可观察？§1.2 无 `activeElement` 提及。**待定**（D4 聚焦范围外，
   但会影响 §3.6 `trusted_click` 的「默认动作」断言）。
4. **`Capabilities.document_write: bool` 与 post-load 口径的关系**：若 post-load = 报错，
   该字段是否要细化为 `"inline_only"`？**待定**。
5. **两个 `Rc<RefCell>` 嵌套（`shared` 内含 `tree`/`writes`）**是否必要？我倾向**扁平化**
   （把 `tree`/`writes` 提到 `BrowsingContext` 直接字段或减少一层），可显著缩小运行期 panic 面；
   但这会改动 §1.2 多处签名，属**架构取舍**，请主理人裁决。
6. **`html5ever` 的 `TreeBuilder` 作为 `TokenSink` 时，`Sink::Handle` 的实际类型**：
   施工图写 `TreeBuilder<NodeId, DomSink>` 且 `ParseOutcome::BlockedOnScript(NodeId)`。
   源码层面 `TreeBuilder<Handle, Sink>` 的 `Handle` 由 `TreeSink::Handle` 决定（`DomSink::Handle = NodeId`）⇒ 类型自洽；
   但 **`TokenSinkResult::Script(node)` 里 `node` 是 `Handle`（即 `NodeId`）**，需 S8 全栈跑一次确认
   **`pop()` 出来的就是 `<script>` 元素本身**（而非其父）。**建议 S8 首步保留**（R2 的回归价值仍在）。

## 7. K-11 消解后的增量观点（辩论期补告；边界④更新为「不再作『待 K-11』处理」）

**若 module 脚本最小纳入 G2，我看到的最大技术风险与必要约束：**

1. **暂停点对 `type` 无感（最大风险）**：`tree_builder/mod.rs:245` 只看 `local_name!("script")`，
   `<script type="module">` **同样**触发 `RawData(ScriptData)`、同样在 `</script>` 产生 `Script(node)` 暂停点
   （`rules.rs:745`）。⇒ 驱动若照 classic 分支**就地执行**，模块脚本会被**同步插入解析中途执行**，
   违反 defer 语义且可观测（模块看不到其后的 DOM）。**必要约束**：驱动在 `Script(node)` 处先看 `type`，
   `module` ⇒ 记入 **deferred 列表 + 立即 `resume()`**，**永不**在暂停点执行。
2. **执行时机必须是「解析完成后、document order、`readyState=interactive/DOMContentLoaded` 之前」**，
   且经 `plane.with_page_script`（否则断链 2 未修时 `__iv8__` 可见）。
3. **TLA / 动态 import 会把「解析后同步执行」变成异步等待**：带顶层 await 的模块图求值不再同步，
   需要与 `fetch` **同一套 parked-awaiting-promise 机制**（复用 B-6 的 `HandleLease` 表 + B-9 的停泊态）。
   ⇒ G2 最小化时我建议**具名排除 TLA**（`PageErrorKind::ModuleTopLevelAwaitUnsupported`），
   否则会静默啃掉 `run_until` 的有界性；动态 import 因已转绿可纳入，但同样走 parked 路径。
4. **必须复用 G1 既有件**：`MemoryModuleHost` + `ModuleRegistry`（同 URL 同 namespace，`module_host.rs`）
   + `Realm::eval_module(src, url)`；**每个模块要有 base URL**（`import.meta`），内联模块需合成 URL——口径要登记。
5. **模块图 fetch 一律走 OfflineBundle 同步查表**；未命中与 classic 外部脚本同款（parked 或具名错误）。
6. **错误语义**：`eval_module` 失败应作为**可在 `run_until` 观测的错误**上报，**不得**静默跳过；
   与 §3.4 `load_waits_for_blockers` 的关系（模块是 defer，**不是** load blocker）须在 ADR 写明。
7. K-11 的「空返回纪律」条款（ADR-0015 在办）应同时约束 G2 新回调（`__iv8_fetch` 之外的动态 import 桥），
   避免同一断言面在 G2 复发。
