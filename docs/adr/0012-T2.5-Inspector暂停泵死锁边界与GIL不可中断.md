## 问题

技术方案 §6 要求「暂停期间运行受控的消息泵」，并明文**禁止**两件事：

1. 回调中再次同步 eval 同一 Context；
2. 持 GIL 等待页面线程。

许清楚 §4 Q3 进一步把它拆成三条候选死锁路径，要求 T2.5 逐条测绘：

| 路径 | 因子 | 含义 |
|---|---|---|
| **GIL 路径** | F1 | 暂停期间宿主回调进 Python ⇒ 与 Python 侧线程互相等锁 |
| **重入路径** | F2 | 宿主回调中再次同步 eval 同一 Context |
| **锁序路径** | F3 | 第二线程需要触碰同一 Isolate ⇒ 与页面线程抢 `v8::Locker` |

T2.5 的性质是**边界测绘**，不是「跑通就行」：产出必须是一张
**条件表**（什么条件下死锁、什么条件下不死锁），而不是单一结论。

### 为什么「超时机制」本身是交付物的一部分

死锁在测试里的表现是**进程挂住**，不是**测试失败**。
若不做超时，一个真会死锁的探针表现为「CI 卡住」，
**「不死锁」与「根本没测出来」在证据上长得一模一样**。
故本探针把「超时能否把挂起变成结论」列为**第一验收项（D0）**，
在测绘开始之前先自证。

## 实测结果

### D0：watchdog 自证（第一验收项）

刻意构造一个**除 watchdog 外无退出路径**的消息泵（`hang_forever`），
证明超时机制能把挂起变成 `TIMEOUT` **结论**：

```
=== D0 watchdog 自证（第一验收项）===
  PUMP_ENTERED=true
  PUMP_RETURNED=true
  RESUMED_AT=3026ms
  CALLBACK_COMPLETED=true
  WATCHDOG_FIRED=true
  WATCHDOG_FIRED_AT=3025ms
  TERMINATE_REQUESTED=true
  DEBUGGER_PAUSED_SEEN=true
  CHILD_VERDICT=TIMEOUT
WATCHDOG_SELFTEST_OK=true
ASSERT_PASS(a): 超时机制把「必然挂起」报告为结论（TIMEOUT）而非挂住进程
ASSERT_PASS(a2): 自证场景由 watchdog 自行救回，子进程正常退出（未被父进程 kill）
```

三点必须同时成立，缺一不可：

- `WATCHDOG_FIRED_AT=3025ms` 与 `WATCHDOG_MS=3000` 吻合 ⇒ watchdog **不是**恒定触发；
- 子进程**正常退出**（未被父进程 kill）⇒ 结论来自探针自身，不是外部的超时杀进程；
- `DEBUGGER_PAUSED_SEEN=true` ⇒ 暂停**真的发生了**（否则测的是别的状态）。

`BASELINE_VALID` 的等价物就是 `WATCHDOG_SELFTEST_OK=true`：
它证明后面所有「不死锁」结论不是「没测出来」。

### D0a / D0b：watchdog 的路径与「终止后不复用」边界（PM 需求稿验收项）

#### D0a —— watchdog 走的是 **`IsolateHandle` 路径**（具名断言）

需求稿 D0a 要求输出 `WATCHDOG_USES_ISOLATE_HANDLE=true|false`，如实报告即可。
**实测：`true`。** 代码链条（可 grep 复核）：

```text
main.rs   let isolate_handle = isolate.thread_safe_handle();   // → IsolateHandle
main.rs   Watchdog::start(isolate_handle, ...)
watchdog.rs  fn start(isolate_handle: IsolateHandle, ...)
watchdog.rs  isolate_handle.terminate_execution();              // 跨线程，无需 Locker
```

选这条路径的原因：watchdog 是**独立线程**，而 `&Isolate` 不是 `Send`
（见本 ADR「判定方法」§7 与 `watchdog.rs` 模块文档）。

该事实由 `watchdog.rs` 的 `pub const WATCHDOG_USES_ISOLATE_HANDLE: bool` 承载，
并与 `Watchdog::start` 的形参类型**绑定**：若将来改回 `&Isolate`，形参类型会
**先编译失败**，强制同时更新该常量 —— 避免输出与现实脱节。

输出位置：**每轮子进程证据**里都有
`WATCHDOG_USES_ISOLATE_HANDLE=true`；父进程另有具名断言 `ASSERT_PASS(m)`
**从实跑证据核验**（不是自说自话）。

#### D0b —— **终止后确有复用**，故出断言而非空声明

需求稿 D0b：*若探针在终止后复用 Isolate，必须断言
`CLEAN_RESUME_AFTER_TERMINATE=true|false`；否则应在边界中声明「终止后不复用」。*

**以代码事实为准的核对结论：本探针确实复用。**
`terminate_execution()` 由 watchdog 线程发出后，页面线程**并未重建**
Isolate / Context —— `run_single_combo` 里的
`eval_post_pause(&mut scope)` 就在**同一个 `scope`（同一 Context、同一 Isolate）**
上再跑一次 `1 + 1`。

⇒ 走「有复用」分支，输出断言：

```
TERMINATE_REQUESTED=true
WATCHDOG_USES_ISOLATE_HANDLE=true
CLEAN_RESUME_AFTER_TERMINATE=true      ← 终止发出后，同一 Isolate 仍能干净执行 JS
```

判读（`TERMINATE_REQUESTED` 用于消歧）：

| `TERMINATE_REQUESTED` | `CLEAN_RESUME_AFTER_TERMINATE` | 含义 |
|---|---|---|
| `true` | `true` | **被终止后仍可复用**（本探针实测形态） |
| `false` | `true` | 从未终止，该项平凡成立 |

**一个顺带得到的实测事实（值得 engine-v8 记一笔）**：
全仓库 **没有** 任何 `cancel_terminate_execution()` 调用
（`grep -rn cancel_terminate_execution poc/t2_5_inspector_deadlock/src/` → 0 命中），
而终止之后同一 Isolate 仍能正常执行后续脚本。
即在本构造下（终止发生在**宿主回调内部**、随后异常自然传播出 `script.run`），
**无需**显式取消终止即可继续使用该 Isolate。

⚠️ 该观察**仅在「子进程跑一个组合后即退出」的探针语境下成立**。
生产运行时若要在终止后**长期**复用同一 Isolate，仍应显式
`cancel_terminate_execution()` 并复核 `is_execution_terminating()` ——
本探针**未覆盖**该长期复用场景（见「未覆盖的死锁路径」）。

### D2 成对证据：GIL 路径内部自带的「真/伪互等」对照

这是本 ADR 最重要的一节。设计文档 §3.5 要求「Python 侧函数内 `time.sleep()`
等页面线程」。但 **`time.sleep()` 期间 CPython 会释放 GIL**，于是照字面实现
会得到：Python 线程「在等页面线程」但**没持 GIL** ⇒ 页面线程的
`Python::with_gil` **成功** ⇒ 观测到 `CLEAN_RESUME`。

**那不是「GIL 路径不死锁」的证据，而是「这个构造没构造出互等」的证据。**
照字面实现并报 `CLEAN_RESUME` 就是**假绿**。

故 F1=yes 的每组都跑**三种** Python 侧策略：

| 策略 | Python 侧行为 | Python 侧持 GIL？ | 角色 | 实测分类 |
|---|---|---|---|---|
| `spin_holding_gil` | 纯 Python 忙等（只调 `time.monotonic()`，不释放 GIL） | **全程持锁** | **实验组** | `TIMEOUT`（`GIL_BLOCKED_MS≈6000`） |
| `sleeping` | `time.sleep(50ms)` 循环 | 约 99.9% 时间不持锁 | 与设计文档字面可比 | `CLEAN_RESUME`（`GIL_BLOCKED_MS≈0`） |
| `not_holding` | 仅完成初始化，随后**完全不持 GIL**，在宿主侧等待 | **零** | **确定性对照** | `CLEAN_RESUME`（`GIL_BLOCKED_MS=0`） |

三个独立读数共同支撑对照，缺一不可：
分类（`CLEAN_RESUME`/`TIMEOUT`）、`GIL_BLOCKED_MS`（被阻塞多久）、
`GIL_CONTENDED`（发起时对方**是否真的持锁**）。

实测原文（同一组合、同一二进制，只换策略）：

```
COMBO[5] f1=yes f2=no f3=msg_only
  spin_holding_gil : GIL_BLOCKED_MS=6000  TIMEOUT        WATCHDOG_FIRED=true
  sleeping         : GIL_BLOCKED_MS=0     CLEAN_RESUME   WATCHDOG_FIRED=false
  not_holding      : GIL_BLOCKED_MS=0     CLEAN_RESUME   WATCHDOG_FIRED=false
```

### 测量局限（**必须读**；一次真实翻转事故的产物）

本节的结论不是理论推演，而是**一次实测事故**逼出来的。

**事故**：架构师独立重跑时，组合 5 + `sleeping` 从 `CLEAN_RESUME`
（`GIL_BLOCKED_MS=0`）**翻转**为 `TIMEOUT`（`GIL_BLOCKED_MS=10183`）。

**根因分析（两条，均已修）**：

1. **就绪标志的语义不严** —— 首版把 `import("time")` 放在「置就绪标志」
   **之后**。于是标志说「我准备好了」，实际 Python 线程还在持着 GIL 做导入；
   页面线程据此发起的 `with_gil` 等的是**对方的导入**，而不是设计中的条件。
   ⇒ 改为：**准备全部完成后**才置标志。
2. **对照组的 GIL 重获取过于频繁** —— 首版 `time.sleep` 分片是 5ms，
   Python 侧每 5ms 就「释放→重新获取」一次。在过载机器上，页面线程的
   `take_gil` 可能连续多轮抢不到 ⇒ 对照自身的 `GIL_BLOCKED_MS` 被抬高。
   ⇒ 改为 50ms 分片（Python 侧约 99.9% 时间不持锁），并**新增
   `not_holding` 作为持锁时间为零的确定性对照**。

**残留风险（如实登记，不掩盖）**：

`TIMEOUT` 的判据是「watchdog 是否到点」，而 watchdog 只看**墙钟**。
因此**任何**超过 watchdog 的调度延迟都会被计为 `TIMEOUT`，
即便它与 GIL 互等无关。这是判据本身的局限，消不掉，只能**限制其影响**：

- 用 `not_holding`（持锁时间为零）作**严格对照**：它若仍 `TIMEOUT`，
  说明结论不可信，而**不是**「GIL 路径也会死锁」。
- 新增 `MEASUREMENT_SUSPECT=true` 证据行：**对照策略一旦超时即自动标红**，
  使这类运行无法被悄悄计入「GIL 路径会死锁」。
- 输出顶部打印 `DERIVED_*` 派生常数（`DERIVED_PYTHON_MAX_HOLD_MS` 等），
  使「读数是否越界」当场可判。

**关于那次翻转读数的归因（已定论收口）**：该读数 `GIL_BLOCKED_MS=10183`
**超过了本配置的理论上界** `DERIVED_PYTHON_MAX_HOLD_MS=6000`
（Python 侧持锁不可能超过该值），这曾是本案唯一的悬点。

经主理人复核其留存日志，**已定论**：该次运行来自**加固前的旧构建**
（即 `COMBO_RUNS=11` 那一代）。证据：

- 该构建日志中 `WATCHDOG_MS=3000`（默认值，未调大）；
- 日志中 **`DERIVED_*` 命中数为 0** —— 旧构建**不打印**该行；
- 旧构建的可配置上界与收尾时序均与加固后不同。

⇒ 结论：**该次翻转是「加固前构建 + 并发负载」共同作用的结果**；
其两个放大机制（就绪标志顺序、对照分片过频）已由
**50ms 分片**与**准备先于置标志的收尾时序**修复覆盖。
本节不再有未决项。

**工程侧已做的加固（本轮）**：
- 上述两条根因修复；
- 握手超时从 500ms 提到 `max(5×watchdog, 5s)`（CPython 初始化过载时可达秒级）；
- 新增 `PYTHON_HANDSHAKE_READY`、`MEASUREMENT_SUSPECT`、`DERIVED_*` 三类证据行；
- 把「分片长度」「握手超时」做成**可复现的诊断旋钮**
  （`IV8_PROBE_SLEEP_CHUNK_MS`、`IV8_PROBE_HANDSHAKE_MS`），
  使这两个失效模式可**确定性地**复现，而不必靠压垮机器去碰运气。

**复现尝试的如实记录**：在 8 核机器上，用旧参数
（握手 500ms + 5ms 分片）在合成负载至 **load ≈ 90** 下各跑 8~10 次，
**未能复现**该翻转（`GIL_BLOCKED_MS` 恒为 0）。故无法断言翻转
100% 由此二因引起；本条按「已定位两个可修脆弱点 + 残余风险已登记」如实记录，
不宣称已完全消除。

**对主结论的影响**：「watchdog 无法打断 GIL 等待」这条**不受影响**，因为它的
证据在 `spin` 运行**内部**即可自证 —— `WATCHDOG_FIRED_AT≈3000ms` 而
`GIL_BLOCKED_MS≈6000ms`：watchdog 在 3s 已到点并调用了
`terminate_execution()`，但阻塞直到 6s（Python 侧兜底到期）才解除，
即 **watchdog 到点与阻塞解除之间差了整整 3 秒**。这个差值不需要对照就成立。

### D5 重入路径：实测后果是「正常返回」，不是死锁也不是 FATAL

技术方案 §6 明文禁止「回调中再次同步 eval 同一 Context」。
实测后果：

```
=== D5 重入路径 ===
D5_REENTRANT_COMBOS=2     D5_REENTRANT_ATTEMPTED=true
D5_FATAL_OBSERVED=false   D5_TIMEOUT_OBSERVED=false
  REENTRANT_OUTCOME=RETURNED_VALUE
  REENTRANT_OUTCOME=RETURNED_VALUE
ASSERT_PASS(j): 重入路径确实被尝试过（D5 不是恒假门禁）
ASSERT_PASS(k): 重入路径的实际后果已定性
```

**结论：在 `v8` 152.2.0 上，宿主回调内对同一 Context 同步重入求值是
「能跑通的」**（`RETURNED_VALUE`：`6 * 7` 求值成功），
既不死锁，也不 FATAL，也不抛可捕获异常。

**但「能跑通」不等于「可以用」。** 这条禁令的正当性来自**可预测性**而非
「会崩」：重入期间 V8 处于**再进入（re-entrancy）**状态，任何依赖
「此刻不在 JS 中」的宿主逻辑（例如把 C++/Rust 侧的栈上临时状态当作独占）都会被打破。
禁令应继续作为**架构约束**执行，理由是「不依赖实现细节」，而不是「实测会崩」。
把它写成「会崩」会在维护者实测「明明能跑」时失去约束力。

### D6 锁序路径：**部分覆盖**（诚实登记，不假装已覆盖）

```
=== D6 锁序 / Locker 路径 ===
D6_LOCKER_COMBOS=3   D6_LOCKER_ACQUIRED=true   D6_LOCKER_CONTENDED=true
ASSERT_PASS(l): 跨线程 Locker 路径已覆盖并给出结论
```

**覆盖了什么**：观测到「页面线程暂停期间，同一 Isolate 的访问权被占用，
第二线程若要触碰它就必须先拿 `v8::Locker`」——即**锁序死锁的前提成立**。

**没覆盖什么**：**没有**真的去 `lock()` 一个非共享 Isolate。
原因（源码核实 + 上游约束）：`v8-152.2.0` 的 `v8::Locker` **只能**由
`SharedIsolate::lock()` 得到（`src/locker.rs:359-370`），而 `SharedIsolate`
只能由 `OwnedIsolate::try_into_shared()` 得到；对普通 `Isolate` 强行构造
`Locker` 会破坏 V8 的锁状态。故本组是**部分覆盖**，已列入「未覆盖路径」。

### C 组：技术方案 §13 的「不推进页面任务」与「暂停可解除」

```
ASSERT_PASS(g): 暂停期间普通页面任务未被推进（技术方案 §13 的「不推进」半边）
ASSERT_PASS(h): 暂停可正常解除，且解除后 Isolate 能继续执行脚本（D8）
```

- **D7**：暂停前把一个 microtask 排入队列，暂停**期间**读它的标记：仍为「未置位」
  ⇒ `PAGE_TASKS_STALLED_DURING_PAUSE=true`。这是 V8 内部任务队列的观测
  （`v8` crate 不提供 `setTimeout`，那是宿主事件循环能力）。
  **宿主级**任务队列本探针没有事件循环，故未覆盖（已登记）。
- **D8**：解除暂停后执行 `1+1` 得 `2` ⇒ `POST_PAUSE_EVAL_OK=true`。

## 结论

**三条候选死锁路径里，只有 GIL 路径会真的死锁；重入路径与锁序路径不会。**

更精确地说：

1. **GIL 路径会死锁，而且 watchdog 打不断它。**
   Python 侧持 GIL 忙等时，页面线程的 `Python::with_gil` **阻塞 5999ms**
   （等于 Python 侧兜底时长），期间 watchdog 在 3000ms 已到点、
   已调用 `terminate_execution()`，但**GIL 等待并未因此结束**。
   只有 Python 侧自行释放才解锁。
   ⇒ **技术方案 §6「执行超时由独立 watchdog 请求 V8 终止」这条对策，
   对 GIL 等待无效。** `terminate_execution()` 打断的是「正在 V8 里执行的 JS」，
   而 `Python::with_gil` 是在 **CPython 内部**等待，V8 看不见。
2. **重入路径可以跑通**，但不应对其形成依赖（理由见 D5 节）。
3. **锁序路径的前提成立但未被完整覆盖**，登记为遗留。

### 对架构的直接影响（必须遵守）

1. **禁止在暂停泵（及任何宿主回调）内同步获取 GIL。**
   必须使用 PyO3 的 `attach`/`detach` 语义，把「进 Python」这件事
   从页面线程的**同步调用栈**上摘出去（例如投递到专门的 Python 执行线程并异步回填）。
2. **执行超时不能只依赖 watchdog。** GIL 等待不可中断 ⇒ 必须额外有
   **Python 侧的自持锁上限**（本探针用 `max_hold_ms = 2 × watchdog` 兜底）。
   没有它，一次 GIL 互等就是**永久**挂死。
3. **暂停期间的消息泵必须真的「不推进」页面任务**（D7 已证可行），
   但也因此**不能**在泵内跑 microtask checkpoint —— 若某功能依赖它，需另设计。
4. **单进程内并存两个 Isolate 必须走 `SharedIsolate`。**
   来源：T2.2 工程师实测（经主理人转达）。本探针的 D6 依赖这条约束
   （本机未独立复现该 FATAL，但源码核实确认 `Locker` 只能由
   `SharedIsolate::lock()` 获得，与该约束一致）。

## 未覆盖的死锁路径（显式登记，**不得默认为安全**）

探针把这三条**打印进输出**（不是只写在文档里），以免被当成「已测」：

```
UNCOVERED=多Context/多Worker并发(T2.5不覆盖,属G4/G6)
UNCOVERED=网络事件在暂停期间到达的处置(本探针无事件循环)
UNCOVERED=同一Isolate被多线程同时eval(超出needs_locker的单线程边界)
```

补记（D0b 相关，见上「D0a / D0b」节）：**终止后长期复用同一 Isolate 的场景未覆盖** ——
本探针在终止后只再执行一次 `1+1` 随即结束子进程；未验证长跑、未验证
`cancel_terminate_execution` / `is_execution_terminating` 的组合。

另有 4 组组合**不可测**（两因子同时为真时归因不可分离）：

| # | F1 | F2 | F3 | 不可测理由 |
|---|---|---|---|---|
| 9 | no | yes | needs_locker | F2&F3 同时为真：重入 eval 与 Locker 锁序互相等待，归因不可分离 |
| 10 | yes | yes | none | F1&F2 同时为真：无法归因是 GIL 互等还是同 Context 重入 |
| 11 | yes | yes | msg_only | 同上 |
| 12 | yes | yes | needs_locker | 三因子同时为真：归因不可分离 |

**`T2_5_PROBE_OK` 不代表「无死锁」。** 它只代表「已覆盖组合的分类都测出来了，
且方法自证有效」。维护者不得把它读成「无死锁风险」。

## 判定方法（这一段比结论更重要）

死锁探针最容易产出假绿，故本节的每一条都是**踩过之后**才写下的。

### 1. 必须有「必然挂起」的自证场景（D0）

否则「不死锁」与「没测出来」无法区分。自证必须同时满足：
watchdog 到点时刻与配置吻合 + 子进程正常退出（非外部 kill）+ 暂停确实发生。

### 2. 必须有「会死锁」的对照（D2）

若所有组合都 `CLEAN_RESUME`，说明探针没有构造出任何危险条件，
而不是系统安全。本探针的 3 次 `TIMEOUT` 就是这条对照。

**对照本身也必须是可靠的。** 只用「在空载时恰好成立」的对照，
等于把结论建在机器的闲忙上 —— 本条教训见上「测量局限」：
对照策略在过载下曾发生翻转，故新增了持锁时间为零的
`not_holding` 严格对照与 `MEASUREMENT_SUSPECT` 自动标红。

### 3. `time.sleep()` 会释放 GIL —— 照字面实现会得到假绿

见上「D2 成对证据」。**这是本探针发现的最隐蔽的坑**：
设计文档的字面要求本身会产出假绿，必须偏离它并说明理由。

### 4. `RESUMED_AT` 必须在**泵退出时刻**记录

第一版实现里 `RESUMED_AT` 是在所有收尾线程 `join` 之后读
`Instant::elapsed()`，量到的是「泵退出 + 收尾」的总时长。
`msg_only` 组合的第二线程会一直跑到 `2 × watchdog`，
于是**不死锁的组也显示 `RESUMED_AT=6002ms`**，看起来像卡了 6 秒。
改为在泵退出时立刻记录（`pump_exited_at_ms`）。

### 5. 每个组合独立子进程

`FATAL`（V8 的 `CHECK` 失败）会直接 abort 进程，只能表现为
「子进程被信号杀死」。**FATAL 本身就是一个可判定的结论**，
故父进程必须能区分四种结局：

| 父进程观测到 | 分类 |
|---|---|
| 子进程正常退出且自报 `CLEAN_RESUME` | `CLEAN_RESUME` |
| 子进程正常退出且自报 `TIMEOUT` | `TIMEOUT` |
| 子进程被**信号**杀死 | `FATAL` |
| 子进程超时未退出，被父进程 kill | `DEADLOCK` |

### 6. 三重超时，任一失效都不会挂住 CI

| 层 | 位置 | 失效时的表现 |
|---|---|---|
| 单组合 watchdog | 独立线程 + `IsolateHandle::terminate_execution()` + `AtomicBool` | 子进程自报 `TIMEOUT` |
| 子进程超时 | 父进程轮询 `try_wait`，超时即 `kill` | 判定为 `DEADLOCK` |
| **进程总硬超时** | 独立线程，180s | 打印 `WATCHDOG_ESCALATED=true` 后 **`exit(70)`** |

`exit(70)` 让 QA 能区分「探针正常完成并报告 `TIMEOUT`」与
「**探针自己都救不回来**」—— 后者在 CI 上是「卡住」，前者是「正常退出」。
该路径**已被实际执行验证**（`IV8_PROBE_TOTAL_DEADLINE_SECS=2` 时 `EXIT=70`），
不是「没测出来的安全」。

### 7. watchdog 里的两件事必须都做，且各自的作用域要写清

`terminate_execution()` 打断「正在 V8 里执行的 JS」；
`AtomicBool` 让「纯 Rust 的挂起循环」自行退出。
本探针的泵是纯 Rust 循环，故**实际起作用的是 `AtomicBool`**。
**注意**：`terminate_execution()` 本身**没有线程限制**
（`IsolateHandle` 版可在任意线程调用，源码注释原文：
「This method can be used by any thread even if that thread has not acquired
the V8 lock with a Locker object」）。早期曾有一版错误说法称
「同线程调用无效」——**该说法不成立，本探针未基于它做任何对照实验**。

## 运行环境要求与负载敏感性（**运行本探针前必读**）

### 要求：**必须在无并发负载下运行**

本探针**不要**与其他 `cargo` / 编译 / 压测任务并行执行。

理由：本探针的结论判据是「watchdog 是否到点」，而 watchdog 只读**墙钟**。
并发负载会拉长 OS 调度延迟，使**对照组**（本应干净地不死锁的那条）也超过
watchdog，从而被计为 `TIMEOUT`。这属于**测量环境伪影**。

### 证据一（正例）：空载双跑与条件表逐项吻合

主理人在**无任何并发 cargo** 的机器上连跑两次，结果**逐字相同**，
且与本文条件表逐项吻合，零 `ASSERT_FAIL`：

```
COMBO[4] f1=yes f2=no f3=none         => TIMEOUT / CLEAN_RESUME   （spin / sleeping）
COMBO[5] f1=yes f2=no f3=msg_only     => TIMEOUT / CLEAN_RESUME
COMBO[6] f1=yes f2=no f3=needs_locker => TIMEOUT / CLEAN_RESUME
组合5 sleeping 分支：GIL_BLOCKED_MS=0     （两轮一致）
组合5 spin     分支：GIL_BLOCKED_MS=6000 / 5999
COMBOS_TRIED=8  COMBOS_DEADLOCK=3  COMBOS_UNMEASURABLE=4
T2_5_PROBE_OK（两轮）
```

> 说明：主理人那次用的是**两策略**构建（`COMBO_RUNS=11`）。
> 自本文「测量局限」一节起，构建已扩为**三策略**
> （`COMBO_RUNS=14`：`spin` / `sleeping` / `not_holding`），
> 新增的 `not_holding` 是**与调度无关**的严格对照。两者结论一致。

### 证据二（反例）：并发负载下对照行被误判

先前主理人观测到组合 5 + `sleeping` 从 `CLEAN_RESUME`（`GIL_BLOCKED_MS=0`）
**翻转**为 `TIMEOUT`（`GIL_BLOCKED_MS=10183`）。两个条件同时存在：

1. 该次运行的机器上 **QA 正在并行跑门禁**（多进程争 CPU）；
2. 该次运行用的是**加固前的旧构建**（`COMBO_RUNS=11` 那一代；
   日志佐证见本文「测量局限」一节的定论段）。

**触发条件是并发负载，载体是加固前构建**；放大机制是本文「测量局限」
一节定位的两个脆弱点（就绪标志语义不严、对照 GIL 重获取过频），
二者**均已修复**。

### 判读规则（**照此执行，不得据负载下的对照翻转改结论**）

1. 对照行（`sleeping` / `not_holding`）在负载下**偶发** `TIMEOUT` 时，
   **先空载复跑复核**，不得直接据此改动结论。
   因为「对照组真的死锁」与「负载延迟被计入」在输出上**不可区分**。
2. 输出里出现 `MEASUREMENT_SUSPECT=true` 时，该次运行的分类**不得**用于判定。
3. 读数若**超过**输出顶部的 `DERIVED_PYTHON_MAX_HOLD_MS`，说明
   watchdog 参数不同或构建过期，应核对 `WATCHDOG_MS=` 与 `DERIVED_*` 行。

### 对主结论的影响：**无**

「watchdog 无法打断 GIL 等待」的证据在 `spin` 运行**内部自足**：
`WATCHDOG_FIRED_AT≈3000ms` 而 `GIL_BLOCKED_MS≈6000ms` ——
watchdog 在 3s 已到点并调用了 `terminate_execution()`，阻塞直到 6s 才解除，
**两者相差整整 3 秒**。该差值不依赖对照是否干净，也不受负载伪影影响。

### 对 CI / QA 的操作含义

- **不把本探针放进与构建并行**的门禁步骤；建议单独串行执行。
- 探针自身已有多重护底（单组合 watchdog / 子进程超时 / 进程总硬超时
  180s → `exit(70)`），故**不会挂住** CI；受影响的只是**分类的准确性**。

## 附带的实测 API 约束（写 `engine-v8` / inspector 集成时会踩）

| 约束 | 说明 |
|---|---|
| `Debugger.enable` 是 `schedule_pause_on_next_statement` 的**前置** | 不 enable Debugger 域，V8 不会真的暂停，泵永不进入 ⇒ 全部「`CLEAN_RESUME`」的假结果 |
| Inspector 类型在 `v8::inspector::` 子模块 | **未**在 crate 根重导出（`src/lib.rs:88` 只有 `pub mod inspector;`） |
| `v8::UniquePtr` 在 crate 根 | `src/lib.rs:193` 的 `pub use support::UniquePtr;`；`support` 模块本身是私有的 |
| `run_message_loop_on_pause` **拿不到 V8 scope** | 签名只有 `&self` + `i32`；且无公开 API 从零构造 `Local<Context>`（`Local::from_non_null` 是 `pub(crate)`）⇒ **泵内无法直接重入 eval** |
| `Function::new` 的回调必须是**不捕获环境**的普通函数 | `MapFnTo` 要求 `Self: UnitType` ⇒ 共享状态走 `Isolate::set_slot` / `get_slot` |
| `Function::new` 返回 `Option`，`Object::set` 返回 `Option<bool>` | 都**不是** `Result`；`v8::String::new` 也是 `Option` |
| `CallbackScope::new(Local<Context>)` 的 `NEEDS_SCOPE = false` | 它**不**新开 `HandleScope`，正是回调内需要的语义（外层已有 scope） |
| `V8InspectorClient` / `Channel` 含 `PhantomPinned` | 但 crate 已用 `Box::into_pin` 处理，且 `V8Inspector`/`V8InspectorSession` 持有其所有权 ⇒ **探针侧不需要任何 pin 相关的 unsafe** |
| **本探针实测为「零 unsafe」** | `src/` 下没有任何 `unsafe {}` 块；`check-unsafe-whitelist.sh` PASS（exit 0）。这是 D9 的上限达成，而非「勉强合规」 |
| PyO3 需 `auto-initialize`，**不是** `extension-module` | 独立二进制用 `extension-module` 会在运行期 `dyld: Library not loaded: @rpath/libpython3.13.dylib` |
| 本机 Python 的 `LIBDIR` 被烘死为 `/install/lib` | python-build-standalone 的打包瑕疵；须由 `build.rs` 探测真实库目录并 emit `link-search` + `rpath` |

## 修正注记（2026-10-12 · G1 落地期 · 「直接影响 1」的适用范围限定）

> **性质**：本注记**限定适用范围**，**不改动原正文语义**（原正文保留，供审计）。
> **触发**：ADR-0014（G1 · D2）采纳「**同线程直呼**」后，发现本文「对架构的直接影响 1」的**字面**
> 「**必须**使用 PyO3 的 `attach`/`detach` 语义」与 G1 的同线程路径不相容
> （评审 A `docs/decision-briefs/2026-10-12-G1-辩论意见-A.md` §D2.3 要求落 ADR 前闭合此点）。

**原正文（「对架构的直接影响」第 1 条）原文**：

> 1. **禁止在暂停泵（及任何宿主回调）内同步获取 GIL。** 必须使用 PyO3 的 `attach`/`detach` 语义，
>    把「进 Python」这件事从页面线程的**同步调用栈**上摘出去（例如投递到专门的 Python 执行线程并异步回填）。

**适用范围限定（本注记的结论）**：

- 该条**仅适用于「回调入口线程未持有 GIL」**的情形（**暂停泵 / 跨线程路径**）。
- **G1 的同线程路径不适用**：G1 下 `eval` 由 Python 侧主动调用，**调用线程本就持有 GIL**，
  回调在同一线程内直接派发、**不发起跨线程阻塞式取锁** ⇒ 无需 `attach`/`detach`。
- **真正的判据不是「是否调用 `attach`/`detach`」**，而是**是否发起跨线程阻塞式取锁** ——
  后者才是本文实测的死锁来源（`GIL_BLOCKED_MS≈6000` / `WATCHDOG_FIRED_AT≈3000`）。

**与既有遗留的一致性**：本文「遗留」已写「`attach`/`detach` 异步化方案**需另起 PoC 验证**」，
即 `attach`/`detach` **本非已实测的既定对策**；G1 采纳同线程路径后，其**适用范围被明确收窄**。
**依据**：`docs/adr/0014-G1-D2-PyO3回调派发-同线程直呼与RAII重入禁令.md` 决策 6。
**本文主结论（GIL 路径会死锁且 watchdog 打不断）不受本注记影响。**
