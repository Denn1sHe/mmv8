## 0. 一句话问题

> 我们要让 Python 能「注册一个函数给 JS 调用」（JS 反过来调用 Python）。我们**已经实测**：
> 如果在这个回调里**同步去抢 Python 解释器的全局锁（GIL）**、而另一个线程正握着它，
> 会**真的死锁**，而且**连超时机制都救不回来**。现在要拍板两件事：
> ① 这个「JS 调 Python」的派发该怎么设计才不踩这个死锁；② 承载它的代码（PyO3 宏产生的那层
> 「绕过安全检查」的代码）该放在哪个 crate，才能不撞上全仓「禁止 unsafe」的铁律。

  （Rust 与 Python 互操作库），让 Python 能控制 JS 运行。有一份硬纪律：**全仓禁止 `unsafe`**
  （绕过 Rust 内存安全检查的代码块），只有 V8 绑定层 `engine-v8` 与探针目录 `poc/` 例外。
- **涉及的模块 / 文件路径**：
  - `/Users/dennis/WorkBuddy/mmv8/crates/sdk-python/`（**PyO3 接口层，本决策主题**；当前只有 5 行占位）
  - `/Users/dennis/WorkBuddy/mmv8/crates/engine-v8/src/`（白名单 crate，可放 unsafe）
  - `/Users/dennis/WorkBuddy/mmv8/poc/t2_5_inspector_deadlock/src/pyside.rs`（**PyO3 接真解释器的先例**）
  - `/Users/dennis/WorkBuddy/mmv8/poc/t2_5_inspector_deadlock/build.rs`（libpython 路径修正先例）
  - `/Users/dennis/WorkBuddy/mmv8/AGENTS.md`（铁律 4 / 5 / 6 / 7）
  - `/Users/dennis/WorkBuddy/mmv8/scripts/check-unsafe-whitelist.sh`（白名单守卫）
- **当前状态**：T2.5 已完成，用真 Python 解释器（3.13.12）实测了三条死锁路径。G1 要把
  「Python 回调」正式做进 `sdk-python`。
- **为什么现在必须决策**：
  1. **死锁风险**：ADR-0012 的结论**直接约束**这个设计；错的设计会挂死进程（而在测试里的表现是

     这可能让 `cargo clippy -D warnings` 直接拒绝构建。**这是铁律 4 与铁律 6 的交叉点**。

## 2. 需要拍板的问题

- **主问题**：「JS 调用 Python 回调」的派发设计 + 承载它的 unsafe 该归哪个 crate。
- **子问题**：
  1. 回调派发时，**谁来持有 GIL**、在**哪个线程**、以**同步还是异步**方式进解释器？
  2. 「回调内禁止再次 eval 同一上下文」这条禁令（ADR-0012 D5）该**怎么强制**（报错而非靠自觉）？
  3. PyO3 宏产生的 `unsafe` 与全仓 `unsafe_code = "forbid"` 是否冲突？若冲突，是
     **把边界移进 `engine-v8`**，还是**把 `sdk-python` 加入白名单**？
  4. PyO3 的构建 feature（`extension-module` vs `auto-initialize`）在「出 wheel」与「跑测试」
     两条路径下如何配置而不互相污染？

## 3. 备选方案（至少两个）

### 方案 A：**同线程直呼**（回调进入前已在解释器内，不二次抢 GIL）

- **做法**：让 Python **主动**调用 `ctx.eval(...)`（此时 Python 线程**本就持有 GIL**），
  宿主回调在同一线程内**直接调用** Python 可调用对象，**不**再次 `with_gil`（线程已持锁）。
  跨线程（watchdog/未来 Worker）路径一律走 V8 的 `terminate_execution`，**不**跨线程等 Python。
- **关键代码**（设计契约原文）：

  ```rust
  // crates/sdk-python/src/callback.rs
  /// 把 Py<PyAny> 包装成 engine_v8::NativeFn。
  /// 前置条件（SAFETY 级）：调用本回调的线程**已持有 GIL**（由 Python 侧主动 eval 保证）。
  pub fn py_callback(name: String, cb: Py<PyAny>) -> engine_v8::NativeFn;
  ```

  ```rust
  // 重入禁令：Realm 内部标志
  // 回调内再次 eval 同一 Context ⇒ 返回 JsErrorKind::ReentrantEval（不是 panic、也不是放行）
  ```

- **优点**：**与 ADR-0012 的主结论完全相容**（GIL 路径的死锁只在「同步抢 GIL 等待」时发生，
  本方案不抢）；实现直接，复用 T2.5 已验证的 `Python::with_gil` 单线程形态。
- **缺点与风险**：跨线程/异步回调（未来 Worker、watchdog 回调）**不适用**，需另设通道；
  「回调里调 Python」与「Python 调 eval」在同一线程上，重入禁令必须真的强制住。
- **长期影响**：为 G4 的异步 Provider 模型留出「另一条通道」，但不能直接迁移。
- **工作量**：小~中。

### 方案 B：**独立 Python 执行线程 + attach/detach 异步回填**（技术方案 §16 字面对策）

- **做法**：宿主回调**不在页面线程**进 Python，而是把「调用 Python 函数」这件事**投递**到
  一个专门的 Python 执行线程，异步回填结果（对应技术方案 §16「宿主回调使用 PyO3 attach/detach
  机制，避免持 GIL 等待页面线程」）。
- **关键代码**（示意，原文形态——ADR-0012 将其列为**未实测**）：

  ```rust
  // 页面线程：不持 GIL，只投递
  let (tx, rx) = std::sync::mpsc::channel();
  python_executor.submit(CallbackJob { cb, args, tx });
  // ... 页面线程继续跑，result 回填后 resolve
  ```

- **优点**：**彻底避开**页面线程与 Python 线程的互等（连「同线程重入」都消失）；
  最贴合 ADR-0012 §「对架构的直接影响 1」的字面对策。
- **缺点与风险**：**ADR-0012 明确登记该方案「未实测」**（§遗留：「`attach`/`detach` 异步化方案
  需另起 PoC 验证」）；需要新增线程与消息通道，复杂度、时序与测试成本显著上升；
  回调返回值变成**异步**，与「JS 同步调用宿主函数」的语义冲突（JS 的 `f()` 期望同步拿到值）。
- **长期影响**：可能成为 G4 异步 Provider 的基础；但 G1 就上会超范围。
- **工作量**：大。

### 方案 C（针对子问题 3 的**unsafe 归属**）：**把 PyO3 边界移进 `engine-v8`**

- **做法**：`engine-v8`（**已**在白名单内）承担 PyO3 模块定义与回调派发；`sdk-python`
  只做「薄转发」（把 `engine-v8` 的能力重新暴露为 Python 面）。
- **关键代码**（对照 ADR-0009 决策 2 的原字面）：

  > ADR-0009 决策 2 原文：「转换**发生在 `sdk-python`**……因此 `sdk-python` 依赖 `engine-v8`
  > 的 `abi.rs` 类型……**不**依赖 `bindings-webidl`。」

- **优点**：`unsafe` 落在白名单内，**不触碰白名单**（守住 ADR-0009「白名单不变」）。
- **缺点与风险**：与 ADR-0009 决策 2 的**字面**「转换放 sdk-python」冲突（需 ADR 修订）；
  `engine-v8` 会多一层 PyO3 依赖（工程量与 unsafe 面都增大）。
- **工作量**：中。

## 4. 证据（原文粘贴）

**证据 1 —— ADR-0012 主结论原文（GIL 死锁实测）**：

```
| 4 | yes | no | none        | spin_holding_gil | TIMEOUT      | 是 | GIL_BLOCKED_MS=5998; WATCHDOG_FIRED=true |
```

> 结论原文：「**GIL 路径会死锁，而且 watchdog 打不断它。** …… `terminate_execution()` 打断的是
> 『正在 V8 里执行的 JS』，而 `Python::with_gil` 是在 **CPython 内部**等待，V8 看不见。」

**证据 2 —— ADR-0012 对架构的直接影响原文**：

> 1. **禁止在暂停泵（及任何宿主回调）内同步获取 GIL。** 必须使用 PyO3 的 `attach`/`detach` 语义，
>    把「进 Python」这件事从页面线程的**同步调用栈**上摘出去……
> 2. **执行超时不能只依赖 watchdog。** GIL 等待不可中断 ⇒ 必须额外有 **Python 侧的自持锁上限**……

**证据 3 —— ADR-0012 重入路径实测原文（D5）**：

```
=== D5 重入路径 ===
D5_REENTRANT_COMBOS=2     D5_REENTRANT_ATTEMPTED=true
D5_FATAL_OBSERVED=false   D5_TIMEOUT_OBSERVED=false
  REENTRANT_OUTCOME=RETURNED_VALUE
```

> 结论原文：「**但『能跑通』不等于『可以用』。** 这条禁令的正当性来自**可预测性**而非『会崩』
> …… 禁令应继续作为**架构约束**执行，理由是『不依赖实现细节』，而不是『实测会崩』。」

**证据 4 —— ADR-0012 附带 API 约束原文（PyO3 构建相关）**：

> | PyO3 需 `auto-initialize`，**不是** `extension-module` | 独立二进制用 `extension-module` 会在运行期 `dyld: Library not loaded: @rpath/libpython3.13.dylib` |
> | 本机 Python 的 `LIBDIR` 被烘死为 `/install/lib` | …… 须由 `build.rs` 探测真实库目录并 emit `link-search` + `rpath` |

**证据 5 —— T2.5 先例说明「为什么它没撞上白名单」**：T2.5 的 PyO3 代码在
`poc/t2_5_inspector_deadlock/`（`poc/` **已**在白名单内），故其 `unsafe` 不违规；
而 G1 的 `sdk-python` **不在**白名单，这是**新情况**。

**证据 6 —— 现有仓库事实（已核实）**：

```
crates/sdk-python/src/lib.rs     → 5 行文档注释，无实现
crates/sdk-python/Cargo.toml     → [lints] workspace = true；[dependencies] 为空
Cargo.toml                       → [workspace.lints.rust] unsafe_code = "forbid"
scripts/check-unsafe-whitelist.sh → WHITELIST=( "crates/engine-v8/"  "poc/" )
```

## 5. 本仓库的既定约束（评审必须在此边界内给建议）

- **铁律 4**（`AGENTS.md:21`）：「unsafe 全仓禁止……仅白名单 crate（`engine-v8` 及显式声明的
  FFI 薄桥）例外，且每个 unsafe 块必须带 `// SAFETY:` 不变量注释。」
- **铁律 6**（`AGENTS.md:23-27`）：把「**PyO3 回调边界（GIL 获取与释放）**」列为高风险路径，
  改动须走决策上报获批。
- **铁律 7**（`AGENTS.md:28`）：`AGENTS.md` 自身 AI 不得修改。
- **ADR-0009 决策 1/2**：类型面落 `engine-v8/src/abi.rs`；`HostValue↔Python` 转换**归 sdk-python**；
  `v8` 只许出现在 `engine-v8/Cargo.toml`；**不新增 workspace 成员**；**白名单保持不变**。
- **ADR-0012 §对架构的直接影响**（原文见证据 2）：禁同步持 GIL 等待；需 Python 侧自持锁上限。
- **ADR-0012 遗留**：`attach`/`detach` 异步化「需另起 PoC 验证」（**未实测**）。
- **质量方案 §3.3 高风险面**：`scheduler` 与 **PyO3 回调边界**永远需要评审批准。

## 6. 本代理的推荐（**仅供参考，等待内部辩论**）

- **推荐方案 A（同线程直呼）作为 G1 的落地形态**，理由：
  1. 它是**加性安全**的：它**从不**在页面线程同步抢 GIL 去等待另一个线程，因此
     ADR-0012 记录的那条死锁路径**在结构上不存在**（不是「没测出来」，是「没这条路」）；
  2. 复用 T2.5 **已实测通过**的形态（真解释器 + 单线程 `with_gil`），工程量小、证据已有；
  3. 方案 B（异步化）是 §16 的字面对策，但 **ADR-0012 自认未实测**，且会让「JS 同步调用宿主」
     的语义变复杂——**G1 超范围**，建议登记为 G4 事项。
- **对子问题 3（unsafe 归属）的推荐**：**先实测**。若 `sdk-python` 引入 pyo3 后
  `clippy -D warnings` 因宏展开的 unsafe 报 `unsafe_code` 错，则：
  **首选方案 C（把 PyO3 边界移进 `engine-v8`，白名单内）**——它守住了「白名单不变」，
  代价是与 ADR-0009 决策 2 的字面冲突，需**修订 ADR-0009**（把「转换点」的 crate 归属明确为
  「PyO3 FFI 薄桥在 engine-v8，纯值转换逻辑在 sdk-python」）。
  **不推荐**把 `sdk-python` 加入白名单（扩大 unsafe 面，与 ADR-0009「白名单不变」相反）。
- **我不确定的点（希望重点看）**：
  1. PyO3 宏**是否真的**会触发 `unsafe_code = forbid`（需工程师做最小实测，见 §7 Q1）；
  2. 方案 A 下「回调内调用 Python」若该 Python 代码本身阻塞（例如等一个锁），是否会形成
     「页面线程被 Python 代码拖住」的次生死锁——G1 是否需要额外的**回调超时**；
  3. 「重入禁令」用 `Realm` 内的布尔标志强制，是否够稳（有没有 V8 层可直接借用的状态）。
