## ① 自拟机制：单位=crate，粒度=具名项，**新增独立门禁**而非改执行器
- **语义（Q1）**：`unsafe_code` lint **是 crate 级**且 `forbid` 不可被 `#[allow]` 覆盖（ADR-0002 已证）⇒ **机制只能 crate 级**；**授权**落**项级**。铁律 4「FFI **薄桥**」= 「唯一理由=跨一条外部边界、unsafe 面小、具名、带不变量注释」；此处边界**不是 C FFI，是第三方纯 Rust trait 的 `unsafe fn` 签名** ⇒「薄桥」是**授权形态**；若走 B 却把大半个宿主搬进桥，则「薄」名不副实。
- **信封修正**：真正需要豁免的**只有签名形态**（`unsafe fn` 声明/实现）**± 真腔体**。而**腔体可为 0**：stylo 侧 `ElementDataWrapper::borrow/borrow_mut` 是**安全 `pub fn`**（`stylo-0.20.0/data.rs:332/344`，`pub mod data` 见 `lib.rs:76`）；`ElementDataMut: DerefMut<Target=ElementData>`（`data.rs:371`）且 `ElementData: Default`（`:287`）⇒ 急切持有 wrapper 后 `ensure_data=self.w.borrow_mut()`、`clear_data=*self.w.borrow_mut()=ElementData::default()` **全是安全操作**。代价=逐元素急切分配（G3 本就逐元素存样式，可接受）。

## ③ 排序与对「腔体输入」的稳健性（Q5/Q6 + 本轮补充）
- **排序：⑤(我的 F=A+独立门禁) > A > ② > E > B**。
- **对「腔体必须存在」的稳健性**：**排序不变**。理由：腔体**是否**存在只改**断言 2 的阈值**（0↔≤2），**不改**「单位=crate、执行器零逻辑改动、编译器强制逐项 allow」这三条判据；且我已证**腔体可为 0**（§①）⇒ 信封**不会**把 unsafe 面从「单文件」推向「多文件」。**唯一会翻转排序的条件**：若 S6 定形发现 unsafe 面 **>2 处且分散于多文件**（未来 CSS/布局扩张），则 **B 重新有竞争力**（把 `forbid` 留给 layout-backend、真 unsafe 全锁进桥）；届时按「unsafe 面/文件数」重评，并优先采用我的 F 断言（文本 + 编译器双保险）。
- **E 的正面对照（本轮必答）**：E 与 A 的**编译器层改动完全相同**（crate 级 lint 无 per-file），唯一差别=**守卫豁免粒度**；但 E 的文本最小化**净增益已被三条抹平**：(i) 编译器 deny 已强制逐项 `#[allow]`（§④·F/H）；(ii) 宏生成的 unsafe **编译器照样命中**（§④·I）⇒「文本检不出」不是真缺口；(iii) 我的 F 用**独立 Rust 门禁**拿到同样的窄化，**且不必改执行器**。⇒ **E 引入了不必要的执行器改动面**（`-e` 语义宽于 `-d`、`-H` 的 BSD/GNU 差异：一旦有 bug 会**削弱全仓**守卫，风险不对称）⇒ **E 劣于 A**。仅当未来出现**同 crate 内多文件、多处**需豁免时，E 才值得重评。
- **A 可选（次优）成立条件**：维护者要求「本轮零新门禁」⇒ A 成立；条件=ADR-0002 修正注记 + `cargo geiger` 基线 + `WHITELISTED_CRATES` 集合化（否则 `workspace_policy.rs:240-250` 直接红）+ `[lints]` 换**逐项全等副本**（`:224-227` 是逐项相等，非「等价集」）。
- **B 的「`forbid` 优势」量化（本轮必答）**：B 是四案中**唯一**让 layout-backend 保持编译器级 `forbid` 的方案，价值 = 「未来 ~3k 行（数据模型/盒树/文本/shadow）**不可能合法写出** 任何自有 `unsafe`（连 `#[allow]` 都会 E0453）」。**但本信封下其值很低**：unsafe 面仅 **5 签名 + 0~2 腔体、集中单文件**，且 (i) deny 已强制逐项 allow、(ii) 宏路径编译器亦命中（I）⇒ A/F 的残余风险 ≈ engine-v8 现状残差（显式 allow + SAFETY 的合法 unsafe）。为此付出 **roster/§16 编号 + crate+1 + 桥不薄 + web-dom 接口扩大** 不划算。**B 的价值函数随「unsafe 面 × 文件数」增长**，故本轮**否**、并列**翻盘条件**（见上）。
- **B 不薄之证**：`TElement` impl 需 `NodeRef` + **opaque 侧表**（ADR-0020 决策 2）+ 逐元素 `ElementData` 存取 ⇒ 搬进桥即搬走宿主核心，否则须**扩大 web-dom 接口**（违边界纪律）。

- **brief 证据 C 的 `forbid_unsafe_fn_repro.txt` 无编译器输出**（记录的是 rustup 组件下载失败 `os error 2`）⇒「语言级复现」原未落证；我复跑补足：
