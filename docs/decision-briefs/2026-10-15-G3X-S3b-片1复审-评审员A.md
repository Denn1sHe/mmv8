## 三条候选假设：全部与真因无关（可关闭）

- **① 不同 global 代理**：不适用——**根本没有 eval**（且 `control.rs:7-14` 定稿为「单 Realm 双模式」，`control_eval` 与页面范围同一 Realm/global）。
- **② pump 期拿到生命周期外 realm 视图**：不成立——`run_until` 以 `let Self { runloop, shared, plane, .. } = self;`（`page.rs:359-365`）解构，交给 `PageExec` 的是**同一 `&mut ControlPlane`**，无跨生命周期视图；且从未被调用。
- **③ `TimerVerdict` 语义（`Done` 即弃）**：无关——`runloop.rs:208` `Done | Abort => {}` 只决定调度是否继续，**不会撤销已发生的副作用**；而副作用从未发生。

## 修复方向（接线 = 补调用点）与**接线后必然遇到的 3 个决策**

1. **补调用点**：`TaskSource::Timer` 分支内**先取出 `expr`**（`remove` 一次性返回 `TimerEntry`，**借用必须收束在同一语句内**，**不得跨 eval 持 `timers.borrow_mut()`**——ADR-0016 借用纪律），**再** `self.plane.with_page_script(|p| p.realm_mut().eval(&expr))`。
2. **错误面（须先定）**：`run_task` 返回 `Result<_, SchedulerError>`，而 eval 产出 `JsError`；`SchedulerErrorKind` 现仅 `Closed|Internal|Reentrancy`（`error.rs:10-12`）。JS 异常按浏览器语义**不应致命**⇒ 建议**捕获并登记**（注意 `with_page_script` 的 `catch_unwind` 只管 panic，**`eval` 返回的是 `Err`，必须显式处理**），或扩 `SchedulerErrorKind`。
3. **重入**：eval 期间 JS 可回调触 `shared`/runloop ⇒ 走既有 `Reentrancy` 守卫（`runloop.rs:119-120` 已有该语义与非 panic 断言），`TaskVerdict` 取 `Done` 即可。
4. **勿与工作树改动混淆**：未提交的 `perform_checkpoint()`（ADR-0026 §6-2 微任务冲刷）是**另一件事**；本回调是直接赋值，不经微任务。

## 防再发（建议入教训族）

**禁止以 `#[allow(dead_code)]` 掩盖「WIP 未接线」的字段**：本仓存在「停报但保留 WIP 形态」的做法，而 `allow(dead_code)` 恰好把唯一能自动指出「调用点缺失」的信号静音。建议：此类 allow 必须附**具名停报条目**且条目里写明「**调用点缺失**」（而非「路径看似正确」）；或在 CI 增一条 `#[allow(dead_code)]` 白名单/审计（每个实例须有对应 `#[ignore]` 测试 + 待办编号）。

> **一句话**：不是 realm/global/verdict，而是 **`plane` 从未被用**（编译器早已知情，被 `allow(dead_code)` 掩盖）；修复 = 补调用点 + 定错误面 + 走 Reentrancy 守卫。
