# ADR-0010：T2.2 结论 —— V8 时区是**进程级**的，一 Profile 一 Isolate **不能**解决隔离，必须走进程边界

- 状态：**已接受**（PoC 实测；判定方法自证有效）
- 日期：2026-10-12
- 关联：`docs/TASKS.md` 的 T2.2
- 探针源码：`poc/t2_2_clock_tz/src/main.rs`
- 运行方式：`cd poc/t2_2_clock_tz && cargo run --offline`
- 依赖：**仅 `v8 = "152.2.0"`，无 PyO3**（实测已确认不需要，见文末「附带的实测约束」）

---

## 问题

技术方案 T2.2 要回答：**逻辑 Date 与不同 Profile 的时钟/时区隔离**「走不走得通」。

harness 原始表述（同 T2 表）：

> 逻辑 Date 与不同 Profile 的时钟/时区隔离（**V8 时钟是 process-global，
> 不能假设设个变量就隔离**）

关键在于 V8 侧**有没有**「指定时区」的入口。编排者已从源码核实并写入
`docs/orchestrator-facts-2026-10-12.md`：

- `Isolate::date_time_configuration_change_notification(&mut self, time_zone_detection: TimeZoneDetection)`
  在 **Isolate** 上，只收 `Skip | Redetect` 枚举，**不接受「指定时区」参数**；
- `v8::icu::set_default_time_zone(&str) -> bool` 文档原文明说
  「**This mutates process wide state**」；
- `Date` 类型只有 `new(scope, f64)` 与 `value_of()`，**无时钟注入 API**。

**要验证的假设**：「多 Profile 共用一个 Isolate、只切 Context 换时区」**很可能走不通**。
本 ADR 的任务是把这个假设**证实或推翻**，并给出可行的隔离边界。

---

## 实测方法（先说怎么测，再说结论）

### 关键设计：RAII 时区守卫

因为 `set_default_time_zone` 改的是**进程级状态**，一旦设错会**污染后续所有实验**。
探针用一个 RAII 守卫在每个实验结束时**还原**为 `UTC`，避免实验间互相污染——
这一点在输出里可直接看到（`iso0={UTC}`）。

### 三段实验

| 实验 | 做法 | 回答什么 |
|---|---|---|
| **EXP0** | `set_default_time_zone(Asia/Tokyo)` → 建**两个** Isolate → 读时区 | 基线自证：同一时区下两个 Isolate 读数**相等**且等于期望偏移（`a`） |
| **EXP1** | `set_default_time_zone(A)` → 建 A、读；再 `set_default_time_zone(B)` → 建 B、读 | 两个 Isolate 是否各读到不同偏移（`b`/`c`） |
| **EXP1c** | `Date()` → `set_default_time_zone` → `TimeZoneDetection::Skip` → `date_time_configuration_change_notification` | 「override + 刷新缓存」能否让 Date 跟随 |
| **EXP2** | **只改进程全局设置**（不对 B 做任何 per-isolate 配置） | **进程级直接证据**：B 的读数是否也跟着变（`d`/`e`） |
| **EXP3** | 两个 Isolate 的 `Date.now()` 与宿主墙钟对比 | 时间值本身的二值结论（`f`） |
| **EXP4** | JS 侧 `Date` 兼容层：宿主喂 `t0`/`t1` | 替代路线最小可行性（`g`） |
| **EXP5** | `set_default_time_zone("Etc/Unknown")` | 设置失败分支必须被拒（`h0`） |
| **EXP6** | 自证对照：`refresh(Skip)` 读 Tokyo −540；另测 `Redetect` 会把刚设的时区改回；全新 Isolate 首读即取当前全局值（**缓存懒填充**） | 证明「override 生效」这条路径本身成立（`h2`/`h3`） |

> **两处探针自身的编号不一致（请 eng-t25 补，不影响任何结论）**：
> 探针文件头的「实验结构」清单列了 EXP0~EXP5，而代码里的分段横幅只到
> `=== EXP6 自证：Skip vs Redetect、缓存懒加载 ===`。也就是说：
> - **EXP5**（`Etc/Unknown` 拒绝，断言 `h0`）在清单里有名、但**没有独立横幅**；
> - **EXP6**（`h2`/`h3` 两条自证）在代码里有横幅、但**清单里漏列**。
>
> ⇒ 两段实验本身都**真实存在且有效**，只是**编号与清单没对齐**。
> 本 ADR 以**代码为准**。**断言 tag 是权威标识，共 11 条**：
> `a`、`b`、`c`、`d`、`e`、`f`、`g`、`h0`、`h1`、`h2`、`h3`
> （**逐个枚举而非用区间**——因为 `h1` 的存在使 `a~h3` 这种区间写法极易误推条数。
> 本文档早期版本曾误写「12 条」，正是区间写法导致的计数错误，已按实测更正。）
> **提请 eng-t25**：把文件头清单补上 EXP6、或给 EXP5 加横幅，使两者一致。
> **这纯属文档整洁问题，不改变任何已测结论。**

> **EXP2 踩过的一个坑（已修，值得记录）**：第一版把全局设成 A/B **当前已经缓存着的那个时区**，
> 于是「读数没变」既可能是「时区是进程级的」也可能是「设成了同一个值什么都没变」——
> **恒真的假阴性**。修法是**改成设成一个与两 isolates 原缓存值都不同的时区**，
> 这就是断言 `e` 里「目标时区**不同于它原缓存值**（非恒真）」的由来。

> **两个 Isolate 如何同时存活**：探针实测走的是 **`SharedIsolate` 通道**
> （输出行 `TWO_ISOLATES_ALIVE=true （经 SharedIsolate 通道，两个 Isolate 同时存活）`），
> 而非两个 `OwnedIsolate`——原因见下方 API 约束表第 1 条。

## ⚠️ 方法学局限（显式记录，对齐 ADR-0008 决策 3「显式写出已知局限」）

**这一节是本轮最有价值的方法论教训，必须与结论同等显眼。**

### 局限 1：EXP1c 存在**位置依赖**，不能独立成证

**EXP1c 跑在 EXP1a 之后**，此时 Date 缓存**早已在首次求值时建立**。因此：

| EXP1c 能证明 | EXP1c **不能**证明 |
|---|---|
| 「override + `Skip` 通知 ⇒ 刷新缓存后 Date **跟随**新默认时区」 | ❌「同一 Isolate 内 A/B 两个时区可**并存**且互不干扰」 |
| 「运行时 override 这条路本身是通的」 | ❌「时区可以按 Profile 隔离」 |

**若把 EXP1c 的结果命名成「isolated」，就是本次差点犯的错误。**
它测的是**替换**（replacement），不是**隔离**（isolation）。

### 局限 2：为何本轮**不补做** A/B 并存实验

要证「同一 Isolate 内 A/B 并存」需要满足**两个前置**，本轮都不具备：

1. **时区必须在两个 Isolate 各自首次求值前就确定不同的全局值**——
   因为缓存是**首次求值时**从全局填充的，一旦填错就无法回头
   （实测：已求值的 Isolate 不发 `Skip` 通知就一直读陈旧值）；
2. **同一线程不能同时持有两个 `OwnedIsolate`**（见下方 API 约束表）⇒
   必须走 `SharedIsolate`，而 `SharedIsolate` 的迁移语义会引入新的时序变量。

**更根本的障碍**：由于时区是**进程级单值**，在**同一进程内**为两个 Isolate
准备**不同的**全局时区，本身就是矛盾的——它们会互相覆盖。
⇒ **即使补做实验，也只能验证「串行切换时两者都跟随」，验证不了「并存」。**
这正是本 ADR 认定「进程边界是唯一隔离单元」的加强理由。

**处置**：本轮**不扩范围**，将该项登记为**明确未覆盖**（见「机器可验证」），
并给出后续验证方式。**不得**因为本轮没测就默认可行或默认不可行。

### 局限 3：判定方法自证的边界

EXP2（重跑 EXP0 读到 `{UTC}`）证明了 **RAII 守卫生效、实验间无残留污染**——
这是**方法有效**的证据。但它**不能**证明「EXP1c 的读数未被 EXP1a 污染」——
恰恰相反，EXP1c **就是**在 EXP1a 之后跑的（这正是局限 1 的成因）。

## 实测结果（原文）

```
TZ_A=Asia/Tokyo TZ_B=America/Bogota
T_REF_MS=1700000000000
=== EXP0 基线自证：同一时区两个 Isolate ===
  isolate=A tz=Asia/Tokyo offset=-540
  isolate=B tz=Asia/Tokyo offset=-540
BASELINE_VALID=true
TWO_ISOLATES_ALIVE=true （经 SharedIsolate 通道，两个 Isolate 同时存活）
=== EXP1 时区隔离 ===
TZ_ISO_A=Asia/Tokyo
TZ_ISO_B=America/Bogota
TZ_READ_A=-540
TZ_READ_B=300
TZ_PER_PROFILE_ISOLATED=true
```

**⚠️ 上表最后一行 `TZ_PER_PROFILE_ISOLATED=true` 请读下一节，不要直接当成「时区可隔离」。**
探针自身在 EXP1c 处还打印了关键区分标记：

```
TZ_CACHE_PROBE isolate=A after_refresh offset=…
TZ_CACHE_NOT_ISOLATION=true      ← 探针自己声明「这不是隔离」
VERIFY_TZ_GLOBAL_AFTER_REDETECT=…  ← 对照：传 Redetect 会把刚设的时区改回
```

`TZ_CACHE_NOT_ISOLATION` 是探针**主动打印**的自我限定，措辞与本 ADR 结论 2 一致：
**测到的是 override 生效（全局值替换），不是并存隔离。**

同一 isolate、同一默认时区下 `Date()` 稳定；
`toString` / `getTime` / `getTimezoneOffset` / `getHours` 全部**跟随**默认时区变化。

## 关键发现（全部为实测，非推断）

### 1. ⚠️ `TZ_PER_PROFILE_ISOLATED` 这个名字有误导性 —— 它测的是「override 生效」，不是「隔离」

**这是本轮最重要的方法论教训，必须先讲。**

探针曾输出 `TZ_PER_PROFILE_ISOLATED=true`。**该断言名会让人误以为「时区可按 Profile 隔离」，
而它实际证明的是完全不同的东西**：

| 能得出的结论 ✅ | 不能得出的结论 ❌ |
|---|---|
| `set_default_time_zone` + `TimeZoneDetection::Skip` + `date_time_configuration_change_notification` 这个组合**能让 V8 Date 跟随新的默认时区**（override 有效） | **不能**由此推出「时区可按 Profile 隔离」。恰恰相反——时区是**进程级的单值全局**，override 改的是**那一个全局值**，不是每个 Isolate 各持一份 |

**根因（方法学局限）**：EXP1c（override + 刷新缓存）**跑在 EXP1a 之后**，
而 Date 缓存在**首次求值时**就已建立。因此 EXP1c 只能证明
「override 后刷新缓存可让 Date 跟随」，**无法证明「同一 Isolate 内 A/B 两个时区可并存互不干扰」**。

**处置**：
- **建议后续把该断言改名为 `TZ_OVERRIDE_EFFECTIVE`**（或 `TZ_OVERRIDE_FOLLOWS`），
  避免再被误读为「隔离」。本 ADR 保留原名仅为对齐已产出的探针输出。
- 「A/B 并存隔离」列为**未覆盖项**，见「机器可验证」章节。

### 2. 时区与 Date 方法族是**联动**的，不是只影响 `toString`

`toString`、`getTime`、`getTimezoneOffset`、`getHours` **四个全部跟随**默认时区变化。

> 术语（给不懂 Rust 的维护者）：`getTime` 返回「自 1970-01-01 起的毫秒数」，
> 看起来应该与时区无关；但它是**先按本地时区解释时刻、再换算**，
> 所以时区一变它读数也变。

**对架构的意义**：`Date` 的整个方法族都受进程时区影响，
**不能只替换 `Date.prototype.toString` 就以为处理完了时区**。

### 3. **probe C（函数内 `new Date`）测不了** —— 缓存时机的直接证据

设计原计划用「在函数体内 `new Date`」作为探测点，**实测行不通**：
**在首次求值时，V8 的隐式 Date 缓存已经建立了**，函数体内的 `new Date`
读的是已固化的缓存，因此**观察不到**后续的时区变更。

### 4. ⇒ 机制结论：V8 隐式 Date 缓存是**懒填充**的 —— 首次求值时从**进程级全局**取值，此后固化

这是本 ADR 的**核心机制结论**。它的准确表述（经实测校正）是：

| 时点 | 缓存状态 | 实测证据 |
|---|---|---|
| Isolate 创建 | 缓存**尚未填充** | — |
| **首次求值** | 缓存**此刻才**从**当前进程级全局值**填充 | `VERIFY_FRESH_FIRST_READ_OFFSET` / `VERIFY_FRESH_READS_GLOBAL` |
| 之后改全局值 | 该 Isolate 的缓存**已固化、不跟随** | `VERIFY_STALE_READ_NO_NOTIFY_OFFSET`（发通知前仍是 −540） |
| 发 `Skip` 通知 | 缓存**刷新并跟随新全局值** | 补发 `Skip` 后变为 300 |

> **重要校正**：本文档早期版本把这条写成「缓存在 **Isolate 创建**时建立」，
> 并据此推出「必须在首次求值前预 notify」。**实测证伪了后者**——
> 全新 Isolate **首读直接取当前全局值，不需要预 notify**。
> 「懒填充」的准确含义是「**首次求值时才填充**」，不是「创建时就固定、之后无法干预」。
> ⇒ **真正的约束不是「提前 notify」，而是「时区 override 必须在 Isolate 首次求值之前就确定全局值」**。

> 注意发现 1 与发现 4 的关系：发现 1（override 生效但非隔离）是发现 4（缓存懒填充）
> 的**直接推论**——正因缓存填充自**进程级单值**，
> 所以「刷新缓存让全局值跟随」可以做到，而「每个 Isolate 各持一份时区」做不到。

## 结论

**同一进程内任意时刻只有一个生效时区；override 是全局替换，不是并存。
时区隔离必须走进程边界。** 具体四条：

| # | 结论 |
|---|---|
| 1 | V8 的时区是**进程级的单值全局**。官方文档原文即「mutates process wide state」。任一时刻**只有一个**生效时区 |
| 2 | **override 是全局替换，不是并存。** `set_default_time_zone` + `Skip` + 通知能让 Date **跟随**新值——但改的是那**一个**全局值。此行为**不构成隔离** |
| 3 | **一个 Profile 一个 Isolate 不能解决时区隔离。** 两个不同 Isolate 在同一进程内仍共享同一个进程级时区 |
| 4 | 唯一可靠的隔离单元是**进程边界**——即技术方案 §19 的「按 Profile / 时区划分进程池」 |

### 一条重要的连带结论

`probe C` 测不了这件事还有一个**强含义**：
**即使将来 V8 加了「per-Isolate 指定时区」的 API，也未必够用**——
因为缓存是**首次求值时从进程级全局填充**的，而 Profile 的时区往往在
文档解析、脚本执行**过程中**才被 Profile 声明确定。
**这意味着「时区 override 必须在 Isolate 首次求值之前生效」是使用前提，
而 Profile 的时区必须能被提前知道。**

> 注意这条与「预 notify」的区分（实测已证伪后者）：
> 约束在**「全局时区值何时确定」**，**不在**「何时发通知」。
> 新建 Isolate 不需要预 notify；但若它首次求值时全局值还是错的（例如已被别的
> `Redetect` 污染），读到的就是错的值。

## 对架构的直接影响（必须遵守）

1. **`profile` crate 的时区字段必须是「进程启动期即确定」的值**，
   不能依赖运行中途才产出的 Profile 覆盖。若某 Profile 的时区在运行中才确定，
   **该 Profile 不能与其它时区的 Profile 共进程**。
2. **Profile 池的 key 必须包含时区**（技术方案 §19 的进程池划分依据）。
   调度器按 `(profile_id, tz)` 分组，而不是只按 `profile_id`。
3. **禁止**用「在运行中改进程 TZ 环境变量」作为隔离手段——
   技术方案 §6 已明确「避免并发修改进程 TZ」，且实测表明缓存时机使这条路不可靠。
4. **逻辑时钟与时区是两个正交轴**：逻辑时钟（`monotonic_now` / `frame_epoch`）
   归 `scheduler`（见 ADR-0009 与 Q-5 的结论），**不受**本 ADR 的进程边界约束——
   **只有时区需要进程隔离**。这两件事不要混为一谈。
5. **`engine-v8` 的 Isolate 生命周期管理必须按本轮实测约束设计**（详见下方 API 约束表）：
   - **并存多个 Isolate 只能走 `SharedIsolate`**，不能用 `OwnedIsolate`
     （它**构造即 enter**，同线程不可并存）；
   - **多 Isolate 的 drop 顺序必须与创建顺序相反**（`OwnedIsolate` 有该断言，否则 panic）；
   - **RAII 守卫必须先 drop `SharedIsolate` handle**，dispose 之后不得再触碰 Isolate。
6. **不要把「进程级单值」误读成「可以靠多个 Isolate 绕开」。** 结论 2 已说明：
   override 改的是**那一个全局值**。因此**多 Isolate 只解决「生命周期隔离」，
   不解决「时区隔离」**——两者不要混为一谈。

## 附带的实测 API 约束（写代码时会踩）

| 约束 | 说明 |
|---|---|
| ⚠️ **传 `Redetect` 会污染进程级全局值 —— 比「假阴性」严重得多** | 实测（`VERIFY_TZ_GLOBAL_AFTER_REDETECT`）：传 `Redetect` 后 ICU 的**全局时区值本身**被改回宿主探测值（实测为 `Asia/Shanghai`），**不只是**当前 Isolate 的缓存偏了。**一次误用影响进程内所有 Isolate，且污染会持续到下一次 `set_default_time_zone`。** 这与 `icu.rs` 文档「without re-detecting (**and overwriting**) the zone just set here」一致。⇒ **本探针全部 refresh 一律传 `Skip`，这是必需项而非风格偏好** |
| **不需要「首次求值前预 notify」—— 该假设已被实测证伪** | 实测（`VERIFY_FRESH_FIRST_READ_OFFSET` / `VERIFY_FRESH_READS_GLOBAL`）：**全新 Isolate 的首次求值直接读到当前全局值**（Tokyo −540），**无需预 notify**。「缓存懒填充」的准确含义是「**首次求值时才从全局填充**」，而不是「首次求值前必须先通知」。<br/>**正确规则**：notify 是给**已求值过、缓存已填充**的 Isolate 用的——实测（`VERIFY_STALE_READ_NO_NOTIFY_OFFSET`）已求值的 Isolate 不发通知就读**陈旧值**（−540），补发 `Skip` 后才跟上（300） |
| `set_default_time_zone` 返回 `bool` 且**必须检查** | 无法识别的 id（含 `Etc/Unknown`）返回 `false` 且**不改当前值**；远程 Linux 若 tzdata 缺失会静默失败 ⇒ **假绿** |
| **禁用 `Date::new(scope, f64)` 测时钟** | 其实现是 `v8__Date__New(context, value)`——**宿主喂什么就是什么，完全不读 V8 时钟**。用它测**必然假绿**。必须执行 JS（`new Date(T_REF).getTimezoneOffset()`）让 V8 自己查其内部缓存 |
| 时区常量用**全年偏移恒定**的地区 | 本次用 `Asia/Tokyo` 与 `America/Bogota`（均无 DST）。若用 `America/New_York`，跨 DST 边界会偶发失败——这是断言设计层面的选择，不是 API 约束，但同样属于「会踩」 |

### Isolate 生命周期（**对 G1 的 `engine-v8` 有直接影响**）

以下三条是本轮实测踩到并已记录的，**架构师已对 `v8-152.2.0` 源码复核**：

| 约束 | 源码依据 | 对 `engine-v8` 的要求 |
|---|---|---|
| **`OwnedIsolate::new` 构造即 enter**，因此**同一线程不能同时持有两个 `OwnedIsolate`** | `src/isolate.rs:2768-2774` 原文：`pub(crate) fn new(cxx_isolate) -> Self { let isolate = Self::new_already_entered(cxx_isolate); unsafe { isolate.enter(); } isolate }`；模块文档 `:873-875` 明写「the Isolate is entered when it is constructed and exited when dropped」 | 任何需要**多个并存 Isolate** 的场景（例如「多 Profile 各起一个 Isolate」）**必须走 `SharedIsolate`**，不能用 `OwnedIsolate`。这直接约束 G1 的 Isolate 管理 API 形状 |
| **`OwnedIsolate` 必须按创建的**反序** drop，否则 panic** | `src/isolate.rs:2874-2878` 的断言原文：「`v8::OwnedIsolate` instances must be dropped in the **reverse order of creation**. They are entered upon creation and exited when being dropped.」 | RAII 守卫的**结构体声明顺序必须与创建顺序相反**。多 Isolate 的生命周期管理**不能**用同一作用域的普通局部变量 |
| **drop 最后一个 handle 会 `dispose()`，之后任何 API 调用立即 abort 进程** | `IsolateHandleInner::dispose()`（`:2573-2577`）把指针置 `null_mut()`。**Rust 侧的 `IsolateHandle` 方法因此返回 `Option::None` / `false`**（`:2585-2593` `with_isolate_ptr` 用 `NonNull::new(ptr).map(f)` 做了保护、`terminate_execution` 文档也写「Returns false if Isolate was already destroyed」）；但 **`OwnedIsolate` 侧直取裸指针**，绕过该保护 ⇒ **UB / abort** | **RAII 守卫必须先 drop `SharedIsolate` handle**，再做任何收尾；且**绝不在 dispose 之后再触碰 Isolate**。这条对 `engine-v8` 的守卫实现是硬约束 |

> **为什么第 3 条要特别强调**：`IsolateHandle` 的路径有 `Option` 保护、看起来"安全"，
> 但那**只保护了 handle 路径**。同一进程内若还持有 `OwnedIsolate`，
> dispose 之后对它做任何调用都是未定义行为——**这正是 RAII 守卫的顺序约束存在的原因**。

## 机器可验证

探针含 **11 条断言**，tag 逐个枚举为
**`a`、`b`、`c`、`d`、`e`、`f`、`g`、`h0`、`h1`、`h2`、`h3`**
（与 `poc/t2_2_clock_tz/src/main.rs` 实测一致：`grep -c 'check('` 得 **11**，
且 11 个 tag 全部去重后无重复）。

| tag | 测什么 |
|---|---|
| `a` | **基线自证** —— 同一时区下两个 Isolate 读数相等且等于期望偏移，测量方法非恒真 |
| `b` | 两时区偏移不同且符合参考时刻预期（Tokyo −540 vs Bogota +300） |
| `c` | 「两读数不同」来自 per-isolate 缓存：**只通知 A**（不给它任何 per-isolate 配置）它的读数就跟随全局值 |
| `d` | **只改进程全局设置**（未对 B 做任何 per-isolate 配置）后，**B 的读数从 Bogota 变成 Tokyo 的期望偏移** ⇒ 时区是进程级 |
| `e` | 反向复核：A 的读数也从 Bogota 变成 Tokyo 的期望偏移，且目标时区**不同于它原缓存值**（非恒真） |
| `f` | `Date.now()` 的二值结论有证据支撑：两个 Isolate 的读数都贴着同一个宿主墙钟 |
| `g` | JS 侧 `Date` 兼容层最小可行：宿主喂 `t0`/`t1`，`now` 与 `getTime` 同步跟随 |
| `h0` | `set_default_time_zone("Etc/Unknown")` 返回 `false` 且不改当前值 —— 探针检查了返回值 |
| `h1` | 已避开宿主喂值的 `Date` 构造 API 作为时钟证据（必然假绿） |
| `h2` | 对照组自证：`refresh(Skip)` 路径读到 Tokyo 的期望偏移 −540 —— 探针自身时序前提成立 |
| `h3` | 实测确认三条警告：`Redetect` 会破坏刚设的时区；全新 Isolate 首读即取当前全局值（**缓存懒填充**）；已求值过的 Isolate 需显式刷新 |

任一条回归都会使 `cargo run` 以非零退出码结束并打印 `T2_2_PROBE_FAIL`。

**判定方法自证**：`a`（基线自证）与 `h2`（对照组自证）确保方法非恒真——
`h2` 尤其关键：它证明「`refresh(Skip)` 这条路径**本身**能读到期望偏移」，
因此 `d`/`e` 观测到的偏移变化不能被解释为「刷新机制坏了」。

**`d` 与 `c` 合起来才是「进程级」的直接证据**：
`c` 证明 A 的跟随**不需要**对 A 做任何 per-isolate 配置；
`d` 证明**只改全局**就能改变**未被配置的** B。两者合并 ⇒ 生效的是全局值，不是 per-isolate 值。

### 明确的未覆盖项（**本轮不补做，必须登记**）

| 未覆盖 | 为什么没测 | 后续如何验证（建议） |
|---|---|---|
| **「同一 Isolate 内 A/B 两个时区并存互不干扰」** | 见「方法学局限」局限 1 与局限 2：EXP1c 有位置依赖；而要真正验证需**两个 Isolate 在各自首次求值前**设定不同时区，且受 `OwnedIsolate` 不能并存约束（须走 `SharedIsolate`） | **新起一个探针**：① 用 `SharedIsolate` 建 **2 个** Isolate；② 在**各自首次求值之前**分别 `set_default_time_zone("Asia/Tokyo")` 与 `("America/Bogota")` + `Skip` 通知；③ **交错**读数多轮（A→B→A→B），检查是否互相影响；④ 若任一轮观察到互相影响 ⇒ 结论「连并存都做不到」，时区隔离**必须**进程级。<br/>**注意**：Bogota（全年 UTC-5 无 DST）比纽约更稳，理由同 API 约束表 |

**在补做之前，本 ADR 的结论 2 只支持「override 是全局替换」，
不支持「A/B 并存一定失败」。** 这两个结论强度不同，不要混用。

## 附：关于「T2.2 是否需要 PyO3」的更正

早期实现方案中曾写「T2.2 依赖 `pyo3`（abi3）」。**该结论已过时并作废**：
本 PoC 已在**纯 `v8`、无 PyO3**的条件下实测成功（探针 `Cargo.toml` 的
`[dependencies]` 只有 `v8 = "152.2.0"`，已核实）。

**理由**：时区读取只需执行 JS 表达式并读回数字，**不需要 Python 侧参与**。
PyO3 是 **T2.5**（GIL 死锁路径）才需要的依赖，**T2.2 不引入**。
