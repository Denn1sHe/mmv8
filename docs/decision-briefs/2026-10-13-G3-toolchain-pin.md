## 0. 一句话问题

> **本地开发机装的是 Rust 1.92，远程验证机装的是 1.99，而工具链文件写的是「stable（自动跟随最新）」。
> 结果同一个仓库在两台机器上「clippy 门禁」**在不同时间点红**（已经发生过两次）。是否要把工具链
> **钉死到某个具体版本**（两台机器一致），还是维持「跟随 stable」？**

## 1. 背景与上下文

- **这个仓库是什么**：`iv8` 是**自研浏览器运行时**（Rust 主体 + V8 引擎 + Python 契约层）。
  它有**本地（macOS）开发机**与**远程（Linux x86_64）目标验证机**两台，合并前**两台都要过门禁**。
- **涉及文件 / 机制**：
  - `rust-toolchain.toml`（工具链固定入口，本地/远程共用）
  - `.github/workflows/ci.yml`（CI 矩阵，**AI 不得修改**，铁律 7）
  - `AGENTS.md` §开发环境（工具链策略）
- **当前状态**：
  - `rust-toolchain.toml` **只写 `channel = "stable"`**（不固定补丁版本）——见 §4 证据 A。
  - 本地 `rustc 1.92.0`；远程 `rustc 1.99.0`（见 §4 证据 B/C）。
  - CI 矩阵 = `["stable", "1.92.0"]`（见 §4 证据 D）。
  - **已两次因版本漂移导致单端红**（§4 证据 E/F）。
- **为什么现在必须决策**：G3 要引入 **stylo/taffy/parley** 一大批新代码与新依赖，
  **新版 lint 触发概率上升**；若不钉版，G3 的 S14（双端门禁复验）可能反复因版本差异红。

## 2. 需要拍板的问题

- **主问题**：是否把 `rust-toolchain.toml` 的 `channel` 从 `"stable"` **改为精确版本**（如 `"1.92.0"`），
  令本地/远程/CI 三处一致？
- **子问题**：
  1. 钉哪个版本？（本地现成的 1.92？远程现成的 1.99？还是第三个？）
  2. 钉版后，本仓 `rust-version = "1.85"`（MSRV 声明，`Cargo.toml`）如何处置？
  3. 升级流程如何约束（谁能改、是否须独立 PR + 双端复跑）？
  4. 钉版是否**足以**消除「本地能编译、远程跑不了」？（防的是 lint 漂移，不是语法）。

## 3. 备选方案（至少两个）

### 方案 A：**钉精确版本**（`rust-toolchain.toml` 写精确 `channel`）

- **做法**：`channel = "1.92.0"`（或裁决选定的版本）；本地/远程安装同一版本；CI 矩阵与之一致。
- **关键代码**（原文草案）：
  ```toml
  [toolchain]
  channel = "1.92.0"          # 原为 "stable"
  profile = "default"
  components = ["rustfmt", "clippy"]
  targets = []
  ```
- **优点**：① 消除 lint 漂移（G1/G2 两次红均因此）；② 可重复构建。
- **缺点与风险**：① **丢失 stable 的自动修复**（安全 lint 修复要手动升）；② 需**改动**
  `rust-toolchain.toml`（非铁律 7 保护文件，可改，但属**工具链基线**，建议走维护者确认）；
  ③ 若远程**只装了 1.99**，钉 1.92 需要 `rustup toolchain install 1.92.0`（**用户级安装**，AGENTS.md 已授权）。
- **长期影响**：与「固定 revision」的 §19 精神一致；升级 = 一次双端回归。
- **预估工作量**：小。

### 方案 B：**维持 `stable`（跟随最新）**（现状）

- **做法**：不改 `rust-toolchain.toml`；本地/远程各自 `rustup update` 到最新。
- **优点**：拿到最新 lint 修复；零改动。
- **缺点与风险**：**两台机器 stable 时点不同 ⇒ 门禁红的时间点不同**（已两次发生，§4 证据 E/F）；
  排查成本高（表现为「另一端过了这端没过」）。
- **长期影响**：G3 新代码越多，漂移面越大。
- **预估工作量**：零（但**风险成本**持续）。

### 方案 C：**钉「较新的 stable」并让两端对齐到它**（如 1.99）

- **做法**：`channel = "1.99.0"`（远程现成；本地需装 1.99）。
- **优点**：与远程现成版本一致；拿到较新 lint。
- **缺点与风险**：本机也需装 1.99；若 1.99 引入更严 lint，需要先修历史代码（一次性）。
- **长期影响**：同方案 A。
- **预估工作量**：小（+ 一次历史 lint 修复）。

## 5. 本仓库的既定约束（外部建议必须在此边界内）

- **铁律 7**：AI **不得修改** `.github/workflows/**`。**CI 矩阵的改动须维护者批准**（本 brief 的
  「钉版」若同时要改 CI 矩阵，须走批准；仅改 `rust-toolchain.toml` 不在铁律 7 保护清单内）。
- **AGENTS.md 工具链策略**：工具链与开发依赖由 AI 自主安装（**用户级** `~/.rustup` 等），
  **不需逐项请示**；**系统级改动**才须决策上报。
- **ADR-0005 决策 2**：MSRV 采用「**声明即验证**」——`rust-version = "1.85"` **暂不作为门槛**，
  CI 矩阵固定 `stable` + `1.92.0`；真实 MSRV 待 `cargo-msrv` 探测后回写。
- **跨平台纪律**：新增依赖须支持 linux x86_64。

## 6. 本代理的推荐（**仅供参考**）

- **推荐：方案 A —— 把 `rust-toolchain.toml` 的 `channel` 钉到 `"1.92.0"`（与本地/CI 矩阵一致），
  并请维护者决定是否同步把 CI 矩阵收敛。**
- **理由**：① 两次单端红（证据 E/F）都是**版本漂移**造成的**纯 lint**差异，非功能缺陷——
  钉版**直接消除**这类噪音；② 1.92.0 是**本地现成 + CI 矩阵已有**的版本，改动面最小；
  ③ 远程装 1.92.0 属**用户级安装**（`rustup toolchain install`），AGENTS.md 已授权。
- **我不确定的点**：
  1. **钉 1.92 还是钉更新的**？钉 1.92 = 改动最小但放弃 1.99 的修复；钉 1.99 = 需本机新装 +
     可能要先修历史 lint。**请裁决倾向**。
  2. 钉版后，`rust-version = "1.85"`（MSRV 声明）**是否要一起调整**？两者是不同维度
     （钉版 = 构建环境；MSRV = 最低可编译版本），但**同时存在易被误读**。
  3. CI 矩阵收敛（`["stable","1.92.0"]` → `["1.92.0"]`）是否值得——**改 CI 须维护者批准**。
